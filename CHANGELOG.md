## [Unreleased]

### Added

- **Per-repo sandbox definition — `[sandbox]` in `.tick/runners.toml`** — a repository now declares what its runs need on top of the batteries-included base image, in tracked config, instead of forcing a factory-wide image rebuild: `image` (optional; absent means the version-pinned base — the 99% path declares nothing), `toolchain` (`tool@version` pins provisioned through the version manager the base image ships, into the project's persistent cache, resolved on first run and warm after), and `setup` (idempotent, cache-populating commands — `pnpm install --frozen-lockfile`, `go mod download` — run once per checkout, in order, after the clone and before the harness). This closes a gap `[environment]` deliberately cannot: an Environment check is verification only ("test, don't ask") and cannot provision anything. One implementation serves both substrates, so a local worker warms identically to a cloud one — the sandbox entrypoint calls `tk sandbox setup` after its clone, `tk herd spawn` calls the same code on a freshly created worktree, and "once" is once per checkout, recorded by a fingerprint of the declared commands in the checkout's *git directory* (never in the worktree, where it would land in a worker's `git add -A`), so a fresh clone warms again and a repeat call is a no-op. `tk sandbox image | toolchain | setup` is the surface, and the entrypoint shells out to it rather than teaching a shell script to parse TOML, so the tracked config has exactly one reader per language. **The security boundary is the reason this lives in tracked config at all:** `setup` runs arbitrary shell inside a sandbox holding the run's gateway token and GitHub credential, so it is read ONLY from the PR-reviewed file at the submitted SHA — never a tick note, a model, a signal payload, an API parameter or an environment variable — and there is deliberately no flag, field or variable anywhere in the path that supplies one. A failing setup command is a stop (exit 6, terminal — a reboot reaches the identical answer), because a wave started on a half-provisioned sandbox fails in every worker at model prices. Not yet honoured: booting a *declared* `image`, which needs the control plane to read the tracked config at the submitted SHA before it boots anything; until then the container is told which image it got (`TICKS_SANDBOX_IMAGE`) and warns naming both references, so a declared image is never silently ignored.

- **`tk factory setup` — the factory's credential walkthrough** — a BotFather-style first-run walk that configures a personal factory through prompts alone, shaped exactly like `tk channel setup telegram`: one rung at a time, verified live, then persisted. It checks wrangler auth, offers `tk factory deploy` when nothing is deployed, walks the GitHub credential ladder (a fine-grained repo-scoped PAT is the supported first rung; a personal GitHub App for per-run installation tokens is the documented upgrade path in `docs/factory-credentials.md`), and configures the AI Gateway base URL with the provider behind it — Workers AI needing no key at all, since inference bills to the same Cloudflare account. Each rung is proven against the real service before it is stored: a GitHub API call that also checks the token can *write* to the target repository (a fine-grained PAT that authenticates but was never granted the repo is the classic silent misconfiguration), and a model-list call through the gateway with the provider key. Every credential lands in exactly two places — a write-only Worker secret in the operator's own Cloudflare account and `~/.ticksrc` at 0600 — and never in the repository, which is enforced by a test that runs the whole walk inside a git checkout and fails if any secret appears anywhere under it.

- **AI Gateway routing, per-run attribution, ground-truth cost and the kill switch (D17)** — a cloud run's model traffic no longer carries the operator's vendor key. The sandbox is handed the factory's own `/api/gateway` prefix and a **run gateway token** minted per orchestrator boot; the Worker exchanges that token for the provider key, stamps `cf-aig-metadata` with the run and tick ids the token was issued for (dropping any `cf-aig-*` header the caller sent, so an agent can neither misattribute its spend nor opt out of being attributed), and forwards to the operator's own AI Gateway. Three consequences. A run cannot start without a configured gateway: submission is refused with a 503 whose detail names `tk factory setup`, and a base URL pointed straight at a vendor host is refused as the vendor default it is — the container enforces the same rule at boot. `runs.cost_usd` is read back from the gateway's own per-request logs at every observation, filtered by the run id the Worker stamped, and that number — never an agent self-report — is what the cost budget acts on. And revoking a run's token stops its model traffic mid-run at the credential layer, which works on a wedged or adversarial orchestrator that ignores every message it is sent: every boot rotates (the replaced container's token dies before its replacement's is live), every budget trip and operator stop revokes, and finalize leaves no live credential behind. Closeout gets a fresh token, because a stop must still reach review and closeout. `tk factory setup --cloudflare-api-token` adds the optional half of the gateway rung — a Cloudflare API token with AI Gateway read access, proven with a live log read before it is stored — and a factory without one still routes and attributes model traffic but records each run's cost as unknown rather than as `$0`, which `tk factory status` reports as its own rung.

- **Proof that the cloud harness executes tool calls, and a recording of the shapes it sends** — the first cloud run to complete a real agent turn printed `**Action taken**` above a `tk note …` line whose effect nobody could find, and from outside the container two readings were indistinguishable: the harness ran it against an ephemeral checkout the aborted run never pushed, or the harness narrated a command it never ran. The second would be disqualifying, and a run log cannot settle it — a log is the agent's own account of itself. `scripts/verify-harness-tool-execution.mjs` settles it with side effects that outlive the harness: it substitutes exactly one thing, the model (a local OpenAI-compatible SSE endpoint answering a fixed script, so the tool calls are deterministic instead of whatever a 70B model felt like emitting), keeps everything else real — the real `omp` binary, the `models.yml` wiring `cloud/sandbox/entrypoint.sh` writes, the flags it starts the harness with, a real git repository — scripts a `write` call and then a `bash` call that commits, and then reads the disk and `git log` **after omp has exited**. Both effects are there: the file with exactly its bytes, the commit, a clean tree. The harness executes. Two things it deliberately does not prove, because conflating them sends the next diagnosis to the wrong place: whether a given *model* chooses to emit a `tool_calls` frame rather than prose (a model-quality problem on that rung, identical from outside), and whether a run's tracker writes survive (they do not — nothing pushes the container's checkout, which is the abort path, not the harness). The run also **records** what omp puts on the wire once it has executed a tool, into a scrubbed fixture that `cloud/factory/test/gateway-tool-calls.test.ts` replays through the real `workers-ai` translation: the calling assistant turn carries `content` as an empty **string** (not `null`, not parts) beside a `tool_calls` array whose `function.arguments` is a JSON string, and the result comes back as `role: "tool"` with string content addressed by `tool_call_id`. Content parts were the first place omp was found speaking more OpenAI than Workers AI implements, and tool-call and tool-result messages are where OpenAI-compatible implementations diverge hardest — so this half is a recording rather than a reading of the specification: it says what omp sent, it fails loudly when a new omp sends something else, and it pins that the translation collapses the user turn and leaves every tool field byte-identical.

- **`tk factory status`** — reports each rung (deployment, GitHub, gateway, cost telemetry), what is configured and whether it currently works, following the `tk channel status` pattern: live checks by default, `--offline` to skip them so it is safe with no network, and a rejected credential always reported but only turned into a nonzero exit by `--check`. No credential is ever printed — only the account a token authenticates as, the repository it can reach, and the provider behind the gateway.


### Fixed

- **A run's cost budget could not trip: gateway spend was read one page deep** — a live run cost **$49.31 against a $25 budget** and kept going for ~4.4 hours, recording $2.98. The recorded number was 6% of the real one, which is exactly 50/845: the pagination in `fetchRunSpend` read `result_info.total_pages`, and the AI Gateway logs API does not send that field. Its `result_info` is `{count, page, per_page, total_count}`, so `total_pages ?? 1` made the loop's `page >= totalPages` true on the first iteration every time and precisely one 50-row page was ever counted. Budget enforcement was therefore disabled for every run past 50 model calls — silently, because the partial sum was returned as a total, and the tests passed against a fixture that had invented the missing field. Paging now ends on the only end-of-log signal the API actually gives, a page shorter than the one asked for, and no code or fixture reads a field the API does not send. **The class is fixed as well as the line:** the page cap (raised from 20 x 50 = 1000 rows to 200 x 50 = 10,000, an order of magnitude past the 887-call runaway) is a runaway guard rather than a truncation policy — a read that reaches it FAILS with a new `truncated` telemetry kind instead of returning what it counted, which a configured cost budget turns into a pre-boot refusal (jk7), and it carries the floor it did count so a mid-run budget still trips on the largest ground truth available (never lowering a larger number already recorded). An under-count that looks like a total is the specific shape of wrongness that cost money, so it can no longer be produced. Consequence worth stating plainly: **every cost figure this factory reported before this fix is low by the same mechanism** for any run that exceeded 50 model calls — `runs.cost_usd`, the run records in R2 and anything derived from them under-report, and the gateway dashboard is the only correct historical record. Regression tests pin the live `result_info` shape verbatim (no `total_pages`), that more than one page is fetched, that a cap-hit is a failure rather than a total, and end-to-end that an 887-call run trips a $25 budget — against the old logic that last test records $2.78 and the run stops only when it runs out of observations.

- **`tk factory deploy` waits for the container rollout instead of returning while the previous image is still serving** — a deploy reported "Factory ready" and exited 0, and a cloud run started immediately afterwards booted the PREVIOUS orchestrator image; waiting and re-running picked up the new one. The tell was exact: two consecutive runs failed with byte-identical harness output, at the same offset, across a deploy that had rebuilt and pushed a new image. The cause is in `wrangler deploy` itself — it builds the image, pushes it, calls `modifyApplication`, POSTs a rollout, and returns as soon as the rollout has been *created*. The Worker and its bindings update promptly; the container application does not, and nothing waited for it. That is the most expensive kind of false signal, because it makes a fix that WAS correct look like it did not work, and the natural response is to go hunting for a second bug that does not exist — which it cost several diagnose-fix-deploy cycles doing. The deploy now reads the digest-pinned image out of the container application block wrangler prints (anchored on the application name, so the hundreds of `sha256:` digests in the Docker build log above it cannot be mistaken for it) and polls `wrangler containers list --json` until that application reports the same digest and is no longer mid-transition. A rollout that does not converge inside the bound, an application the account does not list, or a deploy whose output named no digest all end the command **nonzero with the reason named** — including that the deployment itself landed and nothing needs undoing — rather than as a success nobody can trust; `--skip-rollout-wait` accepts the unconfirmed state deliberately and says so in the output, where "Factory ready" is replaced by "container rollout NOT confirmed". The confirmed digest is printed, recorded server-side (`factory_deployment_image`), and **stamped onto every run at ignition** (`run_image`), so `tk cloud status <run>` names the image that run actually booted — per run rather than per deployment, because what a finished run booted must not move when the next deploy does, and a run with no recorded image says "unrecorded" rather than staying silent about it.
- **A substrate resolution is now always stated, and only a refused assertion is announced — and this repository's own pin becomes `auto`** — two runs end on harness dispatch with no herdr in sight, and they were not distinguishable. `substrate = "auto"` finding no herdr was **silent** by design; `substrate = "herdr"` finding no herdr was a loud explicit degradation. Silence is defensible on a laptop and wrong anywhere the log is the only record — a cloud boot that resolved `harness` gave a reader no way to tell "there was no herdr here" from "nobody looked" — and the same silence covered both the ordinary path and a config that was quietly wrong. Every decision now carries a statement (`Decision.Resolution`, printed by `tk sandbox substrate` on stderr): quiet for `auto` resolving either substrate, for a terminal `harness`, and for a pin that held — naming what was asked for, what the probes found and what is dispatching; loud, unchanged, for a `herdr` pin the environment refused or a `TICKS_SUBSTRATE` the checkout did not ask for. The loud case now also names `substrate = "auto"` as the setting a repository driven both ways should carry, and the durable note tells the two apart: `reason=auto-no-herdr` for the ordinary path, `reason=herdr-unavailable` for the refused assertion. Keeping the registers apart is the point — a repository that announces a degradation on every ordinary run has taught its operator to ignore the announcement that matters. That is exactly what this repository's own `substrate = "herdr"` pin was doing: it is driven three ways (a local harness in herdr panes; a local harness with **no herdr running**, dispatching subagents — the skill's original mode, and the degenerate case the cloud-factory design calls sacred; and a cloud sandbox with no herdr server), so the pin asserted something untrue of two of them, announced a broken assertion on every local run without herdr, and stopped the first cloud run outright. It is now `auto`, which probes and resolves all three correctly. `runners-config.md` gains the two-register table, the *Pin, or `auto`?* authoring rule, and — because it was proposed and rejected on enumeration after that cloud run — the reasoning for why there is deliberately **no** "where am I running" signal: `auto` already answers correctly inside a herdr pane, outside one with herdr running, outside one without it, and in a container, so a location variable would duplicate a probe, and it would answer wrongly for a local orchestrator driving cloud workers (D19), which is a supported configuration rather than a hypothetical. What a probe genuinely cannot settle — "herdr is reachable but should not be used here" — is what `TICKS_SUBSTRATE` is for.

- **A cloud run resolves the harness substrate instead of aborting on a repo's local herdr pin** — the first cloud run that completed a real agent turn booted, cloned, resolved its model, made a successful model call, read `.tick/runners.toml`, found `substrate = "herdr"`, correctly discovered there is no herdr socket in a container, and stopped — citing the orchestration protocol and recording the runner-state note in the documented format. The agent behaved exactly right; the configuration was what was wrong. Phase 1 of the cloud factory runs "the existing harness substrate (subagents) inside one container", and herdr-in-the-cloud is a door deliberately left open rather than a deliverable, but nothing told the container that: it read a pin written for the repository's LOCAL runs and stopped. The fix is an explicit override, not a rewritten checkout — editing the tracked file inside the container would change the base every worker commits against and put a config change nobody submitted into the run's diff. `TICKS_SUBSTRATE` (`herdr | harness | auto`) now replaces `[orchestration].substrate` for one run, honoured by the Go decision procedure (`DecideOverride`), by the new `tk sandbox substrate` — two lines on stdout, the resolved substrate then the `runner-state:` note line, with the reasoning on stderr — and by the ticks skill, whose substrate decision now starts with the override. The sandbox entrypoint defaults it to `harness`, exports it so everything the harness spawns resolves the same substrate, prints the resolution and the note line in the boot log, and carries both into the orchestrator's prompt with the instruction to record the note on the epic: the protocol requires explicit degradation to be announced and noted, and an override — a deliberate choice rather than a degradation — is held to the same rule, because a substrate nobody announced is one nobody can audit once the sandbox is gone. Fail-closed either way: a value that is not a substrate stops the boot naming the variable (exit 2) rather than falling back to the file, and `TICKS_SUBSTRATE=herdr` in a container still gets the documented explicit degradation instead of a stop. The other `[orchestration]` key a cloud boot inherits, `max_parallel`, is honoured as-is and printed with the resolution — under the harness substrate it is concurrent subagents inside one sandbox rather than independent panes.

- **A cloud run on the Workers AI rung can now make its first model call** — the furthest a live run had reached: container boot, clone, 3/3 pre-flight, model resolution, omp's own provider wiring and a GREEN gateway probe all passed, and then the first real completion came back `400 AiError: Bad input: oneOf at / not met … Type mismatch of /messages/0/content, array not in string`. The design doc's claim that Workers AI models "speak the OpenAI-compatible shape" was doing more work than the endpoint supports: Workers AI's `/v1/chat/completions` takes `messages[].content` as a **string**, while omp sends OpenAI content parts (`[{"type":"text","text":"…"}]`) for user messages and a plain string for the system message. omp has no setting for the wire shape of message content — its provider config takes `baseUrl`, `api`, `apiKey`, `models` and a `compat` block, and that block has no such key — and swapping harnesses for this one rung would make the no-key rung the only one that cannot run the default kind. So the dialect is normalised at the hop that already reads every model request: the factory's gateway Worker collapses content parts into a string on the `workers-ai` route and nowhere else, leaving a conforming body byte-identical and every other provider's body streamed through untouched. A part with no string form — an image, audio, a file — is **refused** with a 400 naming the message index and the part type, because the standing risk of a translation layer is that it silently drops what it cannot express and reaches the model as a prompt with a hole in it. `docs/design/cloud-factory.md`, `cloud/factory/README.md` and `cloud/sandbox/README.md` now read "OpenAI-shaped, with one documented difference handled at the proxy".

- **A repo routed at Workers AI can name its model** — every Workers AI model id begins with `@` (`@cf/openai/gpt-oss-120b`), so the provider-qualified form `.tick/runners.toml` carries is `workers-ai/@cf/openai/gpt-oss-120b` — and the `Model` pattern, written for `vendor/model` shapes, had never met a namespace sigil and rejected it: a factory configured for the design's no-key provider rung could not put that provider's model in `[orchestrator].model`. A segment may now lead with `@`, in that position and nowhere else — `workers-ai/cf@openai/…` and `workers-ai/@/…` are still stops, so the id stays a real constraint rather than a string with a hole in it. Fixed in all four readers that must agree or one file becomes valid for one and invalid for another: `runners-config.schema.json`, the Go loader, the Python reference validator and the pi extension, each with the real id as a test case and the malformed ones held negative. The sandbox entrypoint already declined to prefix a namespace an id carried, so the explicit form flows through untouched; an id that omits the constant `@cf/` still resolves, and `runners-config.md` now states the grammar.
- **A cloud orchestrator no longer boots with a gateway and no model to call** — the first live run to reach the skill loop cloned at the submitted SHA, passed all three environment checks, started the harness, and then sat at "Working..." producing nothing: the container exported gateway base URLs and the run token but `TICKS_MODEL` was empty, there was no `workers-ai` route at all (the documented no-key rung), and a harness with no model does not fail — it hangs, which is worse than an error and exactly the silence the green-start trap exists to catch. Three changes close it. **The model comes from routing:** when the control plane sets none, the entrypoint asks the checkout through the new `tk sandbox model`, which reads `[orchestrator].model` from `.tick/runners.toml` and otherwise resolves role `orchestrator` at the `frontier` tier, falling back to `[roles.implement]` like any unnamed role — so the orchestrator is routed by the same table as every other role. **The provider is part of the model id:** a qualified id (`workers-ai/…`, `anthropic/…`, `openai/…`, `openrouter/…`) selects the gateway route, a bare `claude-…`/alias or `gpt-…` id is recognised as its vendor's, and anything else stops the boot rather than guessing a route; `WORKERS_AI_BASE_URL` is now exported alongside the other three, a Workers AI model repoints `OPENAI_BASE_URL` at its OpenAI-compatible `/v1` route (Workers AI has no vendor variable a harness reads), and the `@cf/` namespace the routing schema cannot spell is restored from `workers-ai/meta/llama-…`. **The route is proved, not assumed:** one bounded, one-token completion goes through the gateway with the run's own credential before the harness starts — the same content gate `tk herd spawn` applies to workers — and a refusal is quoted verbatim with its status, because the factory's gateway errors name `tk factory setup` themselves. Every unusable configuration is now exit 7 with a message naming the file to edit: nothing routed, an unreadable config (told apart from a missing model), a provider that cannot be derived, a `claude` harness paired with a non-Anthropic model, a refused probe, and a gateway that never answers. It runs before toolchain provisioning, setup and the pre-flight, because a run that cannot make a model call is over whether or not its toolchain installed.

- **The pi runner refuses a role written for another kind, instead of handing its model id to `pi`** — `.tick/runners.toml` has one `[roles]` table and more than one reader: `tk herd spawn` compiles a cell into a herdr spawn of that `kind`, while the pi extension behind `/ticks-plan` and `/ticks-run` compiles the same cell into `pi --provider/--model/--thinking` in its own process. Because `model` lives in the kind's own namespace, one table cannot carry a herdr routing and a pi routing at the same time — and the migration off `## Pi Orchestrator` made that concrete: a repo whose roles are `claude`/`codex` had `sonnet:high` and `gpt-5.6-luna:max` resolving straight into `pi --model`, with no provider at all, on every role the deprecated block used to own. The pi reader now takes only `kind = "pi"` cells. Any other kind is **refused, not dropped**: no model is derived from it, the refusal names the cell, the kind and the model it would have passed (`roles.implement.tiers.balanced: kind = "codex" … refusing to derive implement_balanced_model = "gpt-5.6-luna:max"`), and the run blocks with nothing authorized — quietly leaving the model unset would just run the tick on pi's own default, the same silent substitution the spawner refuses for an impossible cell. A tier that crosses kinds is refused at the tier, leaving its sibling tiers intact; `harness = "pi"` does not license another kind; the deprecated markdown block, which was pi-only by its heading, is unaffected. `runners-config.md` → *One table, one kind per reader* documents the rule and the reader/spawner split it belongs to.

- **`.tick/runners.toml` version gate — an older `tk` now says "upgrade", not "57 unknown keys"** — the command surface (`[testing]`, `[evidence]`, `[environment]`) makes a config file that a previous release cannot read, and until now it did not degrade: every `tk herd` command on an older binary died with *"57 validation errors: environment.commands: unknown key; …"*, naming no cause and no fix, the moment somebody ran `tk config migrate`. The compatibility direction that was designed (a new `tk` reading a legacy `config.md`) was fine; its mirror image was never tested. A file carrying the command surface is now **version 2**, every reader — the Go loader and the pi runner's TypeScript one — checks `version` **before** shape, and a file newer than the binary is refused with exactly one line: `.tick/runners.toml is version 2 and this tk understands version 1; upgrade tk (tk upgrade)`. Within a version the reader understands nothing is relaxed: a typo'd key is still a stop that names the key. `tk config migrate` writes the new version — including for a repo an earlier migration already moved, which is otherwise stranded at `version = 1` with version 2 content — and warns that every other checkout needs tk 0.32.0 or newer before the file lands there.


## [0.31.0] - 2026-08-18

### Added

- **Grace-period relay for blocked Herdr agents** — `tk herd wait --relay-blocked-after` parks blocked worker questions locally first, gives a terminal `tk answer` priority during the grace window, and only then escalates unanswered questions through the configured operator channel. The answer is sent back to the same Herdr agent with `agent.prompt`, allowing the wait to resume.
- **Explicit orchestrator relay** — explicitly watched orchestrator panes and other non-tick Herdr targets can now use the same escalation path with agent-scoped durable questions and `tk answer <question-id> <answer>`. The behavior remains opt-in, so ordinary waits do not relay blocked agents or spam operators at the terminal.

## [0.30.0] - 2026-08-16

### Added

- **The operator channel: autonomous runs can reach the human who launched them** — `tk channel setup telegram` pairs a personal bot (token → `getMe` → one-time `/start` code; secrets land in `~/.tick/operator.json` at 0600 with a `TK_HOME` override, never in the repo — a token-shaped string in the tracked mapping is rejected on load *and* save), and three commands use the pairing: `tk tell` for one-way announcements, `tk ask` for questions that park a tick awaiting and block until answered, and `tk answer` as the terminal twin. A per-operator bot rather than a shared one is a structural choice, not a preference: Telegram allows exactly one `getUpdates` consumer per token, so a global bot forces a hosted relay — this ships with zero cloud. Everything degrades safely when unconfigured (`tk tell` exits 4 having sent nothing; `tk ask` exits 4 but still registers the question and parks the tick, which is exactly the park-and-surface behavior that existed before a channel did), so runner prompts call these commands unconditionally.

- **Questions are durable state with two answer surfaces** — a `tk ask` writes a pending entry under `.tick/pending/` before it touches the network, one consumer per repo is elected by file lock (waiters watch their resolution file instead of opening a second poll), and a question an earlier process delivered is adopted by the next consumer, so `--async` in one shell and `--collect --wait` in another work across processes and restarts. The tick, not the chat, is the source of truth: an out-of-band `tk approve` while an ask is blocked wins, and the Telegram message edits itself to say so; a stale button press is acknowledged and changes nothing. `--timeout` deliberately leaves the question open and the tick awaiting (distinct exit 7) — giving up on waiting is not an answer, and a later `tk answer` or a later run still settles it. `--escalate-after` holds channel delivery for a grace window while local surfaces see the question immediately, for the operator who is sitting at the keyboard when the run needs them.

- **Gate verdicts over the channel carry unforgeable human provenance** — an approve/reject press arrives from the *verified bound sender* and is recorded exactly as `tk approve` records a human decision, with the presser's Telegram id in the note; `tk answer` on a gate runs the same actor guard as `tk approve`, so a runner-shaped actor is refused without `--from human`. The epic close-out gate audit accepts a channel press for the same reason it accepts nothing else: the CLI will not let a runner manufacture the claim. (The final review of this epic caught precisely that forgery path in an earlier draft — `tk answer` clearing a gate without the guard — and it was closed before merge.)

- **Rich operator messages** — `tk ask` speaks all four AskUserQuestion shapes on the phone (free text via ForceReply, single-select buttons, multi-select toggle keyboard with Done, and an "Other…" escape into free text), and two optional channel capabilities extend the surface without touching the frozen `Channel` interface: formatted tells (`tk tell --format`, a five-element MarkdownLite — bold, italic, inline code, code block, link — mapped element-for-element to Telegram HTML and Slack mrkdwn in the godoc, with escaping proven single-pass on every path and a `StripMarkdownLite` fallback for channels that never learn to format) and attachments (`tk tell --file` auto-routes photo vs document by extension; `tk ask --photo --gate approve` hangs approve/reject under an image and resolves through the existing pending machinery, settling via caption edit because a media message has no text to edit). A transport that lacks a capability degrades to plain text rather than erroring.

### Changed

- **The runner protocol teaches the channel — and keeps the bar for using it** (`references/agent-runner.md`, `SKILL.md`, `references/tick-patterns.md`) — a routing table settles which situation gets which verb (gates → `tk ask --gate approve`; a blocked worker with the frontier still moving → park + `tk tell`; blocked with nothing left to do → `tk ask` escalation; checkpoint → report + sign-off ask; completion → `tk tell`; planning → never, the human is in-session), workers never touch the channel, and the doctrine sentence survives verbatim: `tk ask` changes the latency of an answer, not the bar for needing one — a question planning could have resolved is still a planning miss and still lands in the retro's interrupt audit. Tells are documented as deaf: a reply to a `tk tell` reaches no consumer, so a tell must never end in a reply-inviting call to action (field-observed the same afternoon it was written).

- **`tk close` on an unrouted `--requires` tick refuses, and the skill now says so** — the previous skill text called routing-by-close "your normal path"; the CLI refuses a runner-shaped close over an approval gate, so the documented route is `tk update <id> --awaiting approval`. The stale sentence was caught live by the first real pairing drill.

## [0.29.0] - 2026-08-15

### Added

- **A claim the diff *writes* is also untested** (`SKILL.md`) — the stale-claims rule catches sentences an epic invalidates; it cannot catch the ones an epic is born with. A tick that adds a safety mechanism usually documents it in the same commit, and that new sentence is asserted rather than tested: it describes what the author intended, which is exactly where an implementation gap hides. Field-observed: a wiki page written by the same epic said an attempts counter "keeps a poison row walking the MAX_ATTEMPTS ladder instead of being reclaimed forever", while the code consumed that counter on only one of the two failure paths — the ladder was counted and had no top, so a row whose delivery threw was reclaimed indefinitely. Grepping old files cannot find that one; treating every new invariant sentence as a test that has not been written yet can.

## [0.28.0] - 2026-08-15

### Changed

- **Slimmer dashboard worker rows** — the row repeated itself twice over: the timer prefixed itself with the status the status column already named (`working … working 4m12s`), and the branch was the conventional worktree prefix plus the tick id sitting in the first column. Both are gone; the row now ends in one unlabelled timer, how long the worker has been alive. ## [0.27.0] - 2026-08-15

### Changed

- **The dashboard orders epics by activity and folds finished ones** — an unpinned board lists every epic with run state, and it listed them by id, so on a project run three finished epics filled the screen above the one actually running and their closed ticks pushed the live wave below the fold. Epics now sort by running workers, then open ticks, then id. "Running" excludes `done` and `idle` (herdr's own terminal statuses) and gone workers — a closed epic keeps its `done` manifests until cleanup, so counting them was what pinned finished epics to the top; `blocked` does count, since an agent waiting on a human is the most active thing on the board. The id tiebreak keeps the order stable across the reloads that fire on a timer and on every filesystem event. An epic whose ticks are all closed folds to a single line with its tick count; epic headers are now cursor rows and `enter` on one folds or unfolds it, while `enter` on a tick still opens the detail view. The fold default is decided once per epic on first sight and never re-derived, so an operator's toggle survives the next refresh and an epic that closes its last tick while being watched does not fold up under the cursor.

- **Mission control is no longer pinned to one epic** (`references/herdr-runner.md`) — the run-start ritual passed `--env TICKS_EPIC=<epic>` when opening the dashboard pane, but `tk herd dashboard` with no `--epic` already watches every epic with run state under `.tick/logs/herd/`. Pinning meant the board kept showing a *finished* epic for the rest of a multi-epic run: live workers, live panes, and an operator reasonably concluding the run had stalled. The ritual now opens the board unpinned, and `TICKS_EPIC` is documented as the deliberate single-epic case (which is what the `ticks://` link handler wants).
- **The stall instinct gets an operational test** (`references/agent-runner.md`) — knowing the rule was not enough: an orchestrator that had quoted the "epic boundaries are waypoints" line still stopped after closing an epic mid-project. The rule now states the test — *end a turn on a dispatch, never on a close* — because the retro-and-close is the most satisfying output of a run and reads like a finished task, which is exactly where the stall lands. A turn whose last action was `tk close` on an epic or its close-out is not finished; the close-out's own acceptance is retro **and** flesh out the next feasible epic, so the same turn plans and spawns the next wave or names the blocker.

### Added

- **Callers' claims are a planning-time constraint surface** (`SKILL.md`) — when an epic changes a shared mechanism, the code depending on it carries sentences explaining why *it* is safe (module headers, invariant comments, published docs), and those sentences do not move with the code. Across four consecutive epics in one project, every final review's most-cited finding was a claim the epic had falsified. Grep the mechanism's name and its guarantee words (`safe`, `no-op`, `cannot`, `always`, `only`) during partitioning, list the hits, and give them to a tick the same way you would a seam file.
- **Docs pages are a constraint surface too** (`SKILL.md`) — an epic that changes a subsystem gives several ticks the same reason to fix the same architecture or decision page, and doc edits look harmless during planning precisely because nobody lists them as files touched. Three ticks in one epic rewrote the same two wiki pages in sequence and merged cleanly *by luck*: prose conflicts are textual, so git resolves them silently into an incoherent merge rather than a conflict a human reviews. Name the pages an epic will touch and give each to one tick, or let the close-out own them all.
- **The review phase is invisible to the operator** (`references/herdr-runner.md`) — review is deliberately not a helper capability, so a reviewer is a harness subagent at the controller checkout: it appears in no pane, in `herdr agent list`, on the board, or in the badges. An operator sees the implementers go quiet and then nothing at all for the length of a whole-epic diff review. Two consequences now stated rather than fixed silently: the orchestrator should *say* when it dispatches a review and roughly what it covers, since the board cannot; and unlike a worker, a reviewer does not survive an orchestrator crash — the review tick stays open and is re-reviewed, which is safe because the pass is read-only.

## [0.25.0] - 2026-08-14

### Added

- **Project-level goal design** (`skills/ticks/references/goal-design.md`) — a protocol for turning an idea into a verifiable project goal *before* any epic is planned: rearticulate → interview → fact sheet → write-back → verify. Pure skill-layer convention, no new tick fields and no CLI commands: the goal statement lives in the project's description and the fact sheet as `[A<n>]`-marked lines in its `acceptance_criteria`. - **Human-in-the-loop planning rules** (`skills/ticks/references/tick-patterns.md`) — *planning is interactive, execution is autonomous.* Human attention is spent during planning, where the human is present and latency is zero; a human tick surviving into execution should be one planning genuinely could not resolve. Adds a three-way triage of every anticipated human touchpoint (resolve questions now, do human setup tasks now, reduce approvals by converting to a test / pre-authorizing / agreeing the bar / batching), a frontier-based question algorithm (compute the frontier of decisions whose prerequisites are settled, prune branches the work itself will answer, look facts up rather than asking, ask the whole frontier in one numbered message with a recommendation each, repeat until empty), graph-shaping rules for the survivors (ask early / block late, split around the decision, target the interface, scrutinize gate edges), a Step 6 in the foundation-first procedure, a *no unresolved decisions* line in the Definition of Ready, and two anti-patterns. The epic retro now treats a mid-run `--awaiting input`/`escalation` as a planning-quality signal into `.tick/learnings.md`.

### Fixed

- **Only a human can clear a human gate** — `ProcessVerdict` closed an `awaiting work` tick on any `approved` verdict without checking the actor, so an orchestrator running as `TK_ACTOR=<runner>:orchestrator` could `tk approve` its own human tick; the tick graph's "a human must do this" edge had no teeth at the state-machine layer, and the routing error even advertised `tk close --force` as a bypass. A verdict from a runner-shaped actor (colon-scoped, or ending in `orchestrator`) is now refused on `tk approve`, `tk reject`, `tk update --verdict`, `tk close --force` over a `--requires` gate, plain `tk close` on an already-`--awaiting` tick, and an epic `--force` cascade over any gated child. `--actor` is provenance rather than authorization, so a runner-shaped `--actor` is refused too. Unchanged: `tk close` on a `--requires` tick that has not been routed yet still routes it to a human — the agent's normal path. `--from human` is the only attestation and stamps the activity actor `human` rather than the runner name, the same durable provenance boundary `tk note --from human` already established. The state machine stays pure: it is shared by the CLI, TUI, tickboard server and cloud client, which have different provenance stories, so the check lives at the write path. This is deliberately not tamper-proof — a local CLI cannot stop an agent from typing the flag — so epic close-out gains a **gate audit** asserting every gated tick was cleared by a human actor, fail-closed like Acceptance Evidence.

## [0.22.0] - 2026-08-12

### Added

- **Dashboard worker timers** — each worker row in `tk herd dashboard` now carries an elapsed-time summary (`working 4m12s · age 9m01s`): time in the current status, and total age since the manifest was written. A worker stuck in one status is the thing an operator is watching for, and a static status column never showed it.

### Changed

- **Normalized `ExitNoRepo` / `ExitNotFound` across every command** — `approve`, `reject`, `merge` and the `tk herd` family already returned typed exit codes for "not in a git repository" (3) and "no such tick" (4); the ~25 other commands wrapped the identical failures with a bare `fmt.Errorf` and exited 1, so an orchestrator could not branch on either condition without parsing message text. Classification is now central: `repoRoot()` itself returns `ExitError{ExitNoRepo}`, and every tick lookup goes through `notFoundIfMissing`, so a command added later inherits the codes instead of opting in. No condition changed from success to failure or vice versa — only the code each failure reports. Observable changes:
  - `tk init`, `create`, `show`, `update`, `close`, `reopen`, `delete`, `block`, `unblock`, `note`, `notes`, `list`, `ready`, `next`, `blocked`, `label add|rm|list`, `labels`, `deps`, `graph`, `roadmap`, `status`, `stats`, `rebuild`, `migrate`, `gc`, `import` and `tui` run outside a git repository now exit **3 (no repo) instead of 1**. Rationale: exit 1 is "the command ran and failed"; an orchestrator that sees 3 knows to fix the working directory rather than retry or escalate.
  - `tk skills install` / `tk skills diff` with no `--dir` and no enclosing git repository now exit **3 instead of 1**, matching every other command's no-repo failure. Rationale: the two commands' own `--help` used to fold "not inside a repo" together with "neither convention directory exists", which are different faults with different fixes (chdir/`--dir` vs. create a skills directory); the latter still exits 1.
  - `tk show`, `update`, `close`, `reopen`, `delete`, `note`, `notes`, `deps`, `graph`, `label add|rm|list`, `block` (target or any blocker) and `unblock` given an id that names no tick now exit **4 (not found) instead of 1**. Rationale: "this id does not exist" is a recoverable, distinguishable outcome — an orchestrator can create the tick or correct the id — and reporting it as a generic failure sent every such caller down the retry path.
  - `tk roadmap <epic>` for an epic absent from the roadmap now exits **4 instead of 1**, for the same reason.
  - Unchanged on purpose: a tick file that exists but cannot be read or parsed still exits 1, never 4 — this is the boundary `tk herd collect` already draws for run manifests, because a caller reading 4 as "never created" would act on damaged state instead of stopping.

### Fixed

- **Codex workers can commit from a linked worktree** — a codex worker started with the verified full-auto pair (`-a never -s workspace-write`) did its work and then could not commit it: a linked worktree's `.git` is a file pointing at `<git-common-dir>/worktrees/<name>/`, so the index, refs and objects a commit writes all land outside the sandbox. `tk herd spawn` now grants that one directory with `--add-dir <git-common-dir>` (resolved with `git rev-parse --git-common-dir`, never assumed to be `<root>/.git`), keeping the sandbox rather than dropping it. Kinds that need it fail closed: an unresolvable path refuses the spawn instead of starting a worker that cannot commit.
- **`tk herd cleanup` no longer stalls on the worker's own RESULT file** — the worker template deliberately leaves `RESULT-<tick-id>.md` uncommitted, and worktree removal (never forced) refuses any dirty worktree, so every cleanup after a successful run failed at remove-workspace. Cleanup now archives that file beside the run manifest as `<tick>.RESULT.md`, removes it and proceeds — only when it is the sole change in the worktree. Any other modification or untracked file still refuses exactly as before; the no-force guard is unchanged.

- **Typed exit-code classification** — `tk`'s exit code now comes only from an `ExitError` found in the error's unwrap chain (`errors.As`); the message-substring heuristics that used to infer exit 2 from text like `accepts N arg(s)`, `unknown flag`, or `invalid argument` are gone. Rationale: exit 2 tells an orchestrator to fix its command line; the command line was correct and the fault was environmental, so the old code sent every such caller down the wrong recovery path.
  - A command that takes no positional arguments (`tk list stray`, `tk status extra`, …) now exits **2 instead of 1**. Rationale: `cobra.NoArgs` phrases its rejection as `unknown command …`, which matched none of the old substrings, so an arity mistake that every sibling validator reported as usage was reported as a run failure.

- **Pi process-tree cancellation** — supervised children and configured commands use POSIX process groups with TERM/KILL escalation (and a Windows-safe fallback); graceful extension shutdown aborts and awaits active run settlement.
