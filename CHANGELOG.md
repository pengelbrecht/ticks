## [Unreleased]

### Added

- **The cloud substrate is drivable from a laptop: `tk cloud spawn / wait / collect / reconcile` (D19, `internal/cloud/*`, `cmd/tk/cmd/cloud_*.go`)** — `substrate = "cloud"` already parsed and already refused `tk herd spawn`, but a *local* orchestrator meeting it had nowhere to dispatch, so it could only stop. The verb family it was supposed to stop *for* now exists, and mirrors `tk herd`'s one for one on purpose: an orchestrator swapping substrates must not have to relearn its commands. `spawn` submits the wave the orchestrator computed (`tick_ids`) after refusing anything that would cost nothing to refuse first — a run whose workers are herdr panes (exit 9, the mirror of `tk herd spawn`'s own gate), a tick that belongs to another epic, a project that cannot dispatch at all — then writes one manifest per tick under `.tick/logs/cloud/<epic>/`. `wait` settles a worker on the only signal a destroyed container leaves: `RESULT-<tick>.md` **committed** on the branch it pushed. `collect` is `internal/herd/collect`'s three checks pointed at the remote instead of a worktree, importing its verdicts rather than restating them, plus a fifth — `unknown` — because an unreachable remote is not a worker that failed and must never be reported as one (the same rule `progress.ts` and `worker-collect.ts` already apply). `reconcile` classifies a wave after the orchestrator dies and never proposes a second worker for a live tick: a run state that cannot be read is treated as ALIVE, since the cost of waiting for a finished container is one poll and the cost of redispatching a live one is two workers on one branch.
- **One lease, wherever the orchestrator sits (`internal/cloud/lease`, `cloud/factory/src/runs.ts`)** — a locally-driven wave takes the *same* RunRoom lease a Workflow-hosted run takes, and the submission now carries `origin` so the holder is legible: "held by run X (local)" is a laptop session to go and look at, "(cloud)" is the scheduled sweep, and those are different next actions. An unparseable origin is a 400 rather than a silent rewrite to `cloud`. An un-enrolled project keeps the local file lease and is refused with that reason — enrolment upgrades the arbiter and never installs a second one (D4: one enforcement point per project), which is why nothing here writes a lease file of its own. A checkout with **no factory configured makes no network call at all** to learn any of this: the degenerate case — a fully local orchestrator, no cloud enrolment, offline forever — stays exactly as it was.

- **`substrate = "cloud"` is a value `tk` agrees with (`internal/herd/config`, `cmd/tk/cmd/substrate_gate.go`)** — `Substrate` knew `herdr`, `harness` and `auto`, which is why the Run Workflow's per-tick fan-out triggers on a submission carrying `tick_ids` rather than on repo config: there was no config to read, and a repository's declared substrate and a run's actual substrate could disagree with nothing reconciling them. `[orchestration].substrate = "cloud"` now parses, validates and resolves. **It is terminal, like `harness`, and for a stronger reason**: the value says *where the workers run*, so a herdr server listening on the orchestrator's own machine cannot change the answer — no probe runs, and the note records `reason=config-terminal`. It says nothing about where the ORCHESTRATOR sits; local judgement with cloud hands is a supported shape, not an accident. **`tk herd spawn` refuses it with a new exit code 9** rather than doing what it did before, which was nothing: it is the herdr substrate's dispatch verb, and a pane here is a second worker on the branch a container is already pushing to. The refusal costs zero herdr dials and names both ways out. `harness` and `auto` are deliberately not refused — neither is dispatched by a `tk` verb, so `tk herd spawn` there is an operator choosing herdr for one worker. **`TICKS_SUBSTRATE` reconciles in both directions**, which makes the sandbox entrypoint's `harness` default load-bearing rather than cosmetic: a container left to inherit a checkout's `cloud` declaration would dispatch containers from inside a container. **No format version bump** — a value is not a key, and an older `tk` meeting `"cloud"` already prints the one line naming the key, the value and the accepted values that the version gate exists to produce; bumping would lock that reader out of every other key for nothing. The enum crosses into `runners-config.schema.json`, so a golden test pins the two in order. Still not real, and said out loud rather than implied: `tk cloud spawn/wait/collect/reconcile` does not exist, so a local orchestrator meeting `cloud` must stop and say so rather than quietly running the wave somewhere else.
- **`run_event` producers: the board finally sees a live run (`cloud/factory/src/run-events.ts`, `run-room.ts`, `run-workflow.ts`, `cloud/worker` `POST /api/projects/:project/run-events`, `internal/tickboard/ui` `live-run-panel`)** — the protocol in `schemas/websocket/messages.schema.json` had existed with NO producers; tick zjp retired its vestigial `ralph`/`swarm` source values for substrate-shaped ones precisely so the first real producer would emit something honest. A cloud run now says what it is doing: `epic-started` before any container exists, `task-started` per tick before its worker is dispatched, `task-completed` carrying the tick's verdict, `epic-completed` at finalize. The Run Workflow publishes through the project's RunRoom, which forwards to the board's new ingest route, which fans the message out to the browsers watching — so a run with no laptop in it is visible from anywhere. **The board is observability, never authority.** Every hop is best effort and none of them can throw: `publishRunEvents` resolves failures into a delivery record, the board sink is bounded by a 3s timeout, an unconfigured board (`BOARD_BASE_URL`/`BOARD_TOKEN` unset) is the default rather than a degraded mode, and a run whose events are all dropped completes and collects identically — pinned by a test that refuses every event and asserts the same verdicts, the same run record, the same state. A tick's `success` on the board is `verdict === "ready-to-merge"` and nothing else: a worker's own `STATUS: DONE` is shown as text because an operator wants to read it, but a report over a branch with no commits is exactly what collect exists to catch, and a badge is not evidence. **`costUsd` can only come from AI Gateway telemetry.** The protocol carries the field and the design doc named the old behaviour — "today `run_event.metrics.costUsd` trusts the agent's self-report" — as the thing being fixed, so there is one door: `gatewayMetrics()` takes gateway.ts's `SpendResult` and nothing else. No builder accepts a bare number, per-tick worker events carry no metrics at all, and a telemetry read that failed publishes NO cost rather than a zero, because unknown and free are different facts about a run. The RunRoom also keeps the last 50 forwarded events on its `/status` probe, delivered or not, so "is this run still alive?" is answerable without a browser — the shape tpl's keeper heartbeat proved works — and the board's panel marks a run whose stream has gone quiet as stale rather than leaving it looking healthy.

- **The worker container entrypoint — `ticks-worker`, and the probe marker dispatch was guessing at (`cloud/sandbox/worker.sh`, `common.sh`, `cloud/factory/src/worker-boot.ts`)** — the dispatch layer landed tested and had nothing to boot. A worker container now has its own run entrypoint: clone at the epic base, branch `tick/<epic-id>/<tick-id>`, run the harness on one tick, commit `RESULT-<tick-id>.md`, push the branch, exit. **One image, two roles, told by which entrypoint is started.** On Cloudflare an image belongs to the containers application rather than to a boot, so a worker runs the same image as the orchestrator; `ticks-orchestrator` works an epic and `ticks-worker` works one tick, and there is deliberately no role flag beside that — a container whose role is the command it was given cannot be started in the wrong one. The role-neutral half of both boots (exit-code vocabulary, gateway and model routing, the harness credential table, the probes, caches, the clone, toolchain provisioning, `[sandbox]` setup, the pre-flight) moved verbatim into `common.sh`, which both source: two scripts that must agree about a credential variable are exactly the shape of the half-applied fix this repo has already paid for, and a fix that lands in one role and misses the other is a whole wave dying the same way at model prices. **The probe marker is defined here.** `worker-dispatch.ts` gates on the *content* of a probe's output and had nothing real to check for; `ticks-worker --probe` proves `tk`, `git` and the harness binary answer and then prints `ticks-worker-probe-ok` — no model call, no clone, so a wave pays it once per sandbox for what it actually proves. The constant travels through the shell, `internal/sandbox` and `cloud/factory/src/worker-boot.ts`, pinned by a shared fixture both suites read, because a marker that drifts between two languages is a wave of containers that all start cleanly and are all discarded. **It does not `exec` the harness**, unlike the orchestrator entrypoint: its whole contract is what happens after the agent stops. The report is **committed** — a herdr worker leaves it uncommitted for a worktree read, but there is no worktree here and `worker-collect.ts` reads it off the pushed branch — in its own commit, with an explicit pathspec, with the agent's `STATUS:` line never rewritten and a header of facts the agent could not know (its own exit status, its commit count, what it left uncommitted) prepended above it. A pushed branch from an earlier attempt is **adopted, never overwritten**; one from another base is left alone and this attempt pushes beside it. **Three new exit codes** keep the classes distinct: `9` work that exists and could not be pushed (the worst outcome — retry), `10` a branch and report on origin with no work commits (the green-start trap's exit counterpart — look at the tick, not the container), `11` a harness that failed, timed out, or exited without writing its report. **Two things the measurement made switches rather than decisions.** Fan-out degrades 3.74x at N=5 and all of it is dependency install, so `TICKS_WORKER_SETUP=always|skip` exists and every boot prints how long setup took — the number belongs in a log, not in somebody's memory. And `TICKS_WORKER_TIMEOUT`, derived by `worker-boot.ts` from the wave's own wait timeout, bounds the harness *inside* that window: the dispatcher's timeout ends in the container being killed, and a killed container pushes nothing, so the bound is the difference between a lost tick and a legible one. Two supporting `tk` surfaces: `tk sandbox model --role/--tier` (a worker resolves the **implement** cell, not the orchestrator's frontier one — routing every per-tick container at it is a silent multiple on a wave's bill) and `tk sandbox worker-prompt`, which renders the same `spawn.BuildPrompt` template a herdr worker gets plus a container addendum, so the two substrates cannot hand the same tick two different jobs. **Not done here:** wiring `dispatchWave` into the Run Workflow (tick `b6e`), and a mid-flight keeper — a worker pushes at exit, which is the stated contract, and collect explicitly still finds a prior attempt's work.

- **The Workers AI default model is measured, not a placeholder — a per-role/tier recommendation with the prices and scores behind it** — `[orchestrator].model` routed at `workers-ai/@cf/openai/gpt-oss-120b`, an id picked because it was visible in a model list. `scripts/bench_workers_ai_models.py` replaces that with a live measurement of what the account actually serves: the catalog and prices from `GET /ai/models/search`, and OpenAI-compatibility, tool-calling and prefix-cache behaviour probed per model against `POST /ai/v1/chat/completions`. The 2026-08-21 run is committed beside the summary (`benchmarks/workers-ai-models/`, `docs/workers-ai-model-selection.md`). **64 models, 29 text-generation, 16 tool-capable**, each priced against a real wave's token profile (`run_62c289d1`: 230 calls, seven ticks, 98.6% input tokens) rather than by headline rate — which reorders the table, because on this platform a cached input token bills at a thirtieth of an uncached one and **publishing a cached rate is not delivering one**: `qwen3.8-27b` advertises $0.05/M cached and billed **0 of 27** post-warm calls at it, while `gemma-4-26b` reports `cached_tokens` at ~100% and its Neurons do not move. The verdicts: **`deepseek-v4-flash-0731` for the balanced implement tier** ($0.28/tick, 53.3 DeepSWE, 23/23 cache hits — 2.2x `gpt-oss-20b`'s list rate and still 14% cheaper per tick), **`deepseek-v4-pro-0813` for the orchestrator** (63.0 DeepSWE, 1M context, and the model the only reconciled production run already ran on), **`glm-4.7-flash` for economy**, and the incumbent priced at **2.06x** the best option with **no DeepSWE score published on any 2026 board**. `qwen3.8-27b` loses outright: 3.4x the cost per tick for 11 fewer DeepSWE points, a 23.8% tokenizer tax measured on the same fixture, and a cache that never fires. Kimi K3 is **not served** here; the K2.x line that is serves as the inventory's weakest graded model. **`review`, `closeout` and the `frontier` implement tier stay on a BYOK frontier model** and the summary says why rather than pretending a Workers AI model reaches them. Two platform corrections fall out: the endpoint now accepts OpenAI content parts on all sixteen tool-capable models (the design's `array not in string` failure was real and the platform moved — `stringifyContentParts` stays as belt-and-braces), and `result_info.total_count` reported **291 against a real 64**, so it is not a page bound. `internal/sandbox/modelbench_test.go` keeps harness, raw file and summary in step, refuses a cache probe of one call, and fails if any artifact carries an operator account id.
- **Per-tick worker sandboxes — the dispatch mechanism, with all three spawn-time defences (`cloud/factory/src/worker-dispatch.ts`, `worker-collect.ts`)** — Phase 2's headline: one container per tick instead of Phase 1's one orchestrator running every tick as a harness-native subagent. The three defences the herd substrate already required are implemented here, not assumed. **Green-start trap**: before any real command runs, a probe runs and its output is checked for the exact expected content — never its exit code, since an `npx` probe for a missing tool prints npm's own version and exits 0 (the class this tick's own description names twice: an npx probe returning npm's version, a Codex self-update swallowing the gate). A container that starts cleanly and answers wrong, or not at all, or never finishes, is caught and never counted as launched, and the real work command never starts on it. **Confirmed dispatch**: after the real command starts, `confirmDispatch` waits for a running state *plus* produced output — not merely that starting the process was accepted — while still recognising a worker that reaches a terminal state before ever being sampled `running` (a trivial tick can finish before the sampler ever looks), and reports an unconfirmed dispatch as unconfirmed rather than silently downgrading it to "never launched" (`internal/herd/spawn`'s `DispatchUnconfirmed` is the precedent — the durable layer decides, not this wait). **Expiring liveness**: `teardownWorker` reads a fresh liveness check immediately before `killProcess`, never trusting an earlier observation the container could have outlived in the meantime (a GitHub round trip sits in between, in the real flow) — a container that died between confirm and teardown is detected before anything destructive runs on it. **Collect reads only what survived in git**: `worker-collect.ts` ports `internal/herd/collect/collect.go`'s three checks (commits beyond base, a `RESULT-<tick-id>.md` with a recognisable `STATUS:` line, an empty `.tick/` boundary diff) onto GitHub's compare and contents APIs, because a worker sandbox pushes and exits and there is no local worktree left to read — and structurally, a `WorkerCollector` never receives a sandbox handle at all, so it cannot read terminal output even by accident. `dispatchWave` fans a wave out with `Promise.all`, proving "N ticks run in N containers concurrently" rather than working through them one at a time. **Scope drawn deliberately**: this lands the dispatch mechanism itself, fully unit-tested against the same `SandboxBinding` fake seam `run-workflow.ts` already uses (23 + 16 tests, no real container). It does not wire a `TICKS_PHASE=worker` entrypoint into `cloud/sandbox/entrypoint.sh` (what a worker container actually executes to clone/implement/push is undecided and belongs to whichever tick builds it), and it does not wire `dispatchWave` into `RunWorkflow` or an HTTP route (`tk cloud spawn/wait/collect` is tracked separately as tick `bmo`). Kuf's benchmark closed the cost objection (a fully cold wave of six costs 2.5¢); this tick's own design note is what it answers: the fan-out degradation kuf measured is entirely in dependency install, not the image pull, which is why nothing here tries to make one image serve N boots faster — that was already settled as a deployment-time, not a per-boot, choice.

- **Sandbox start is measured, not assumed — a committed harness, raw numbers, and three decisions settled** — Phase 1 boots one sandbox per run and Phase 2 boots one per tick, which is where start cost multiplies by fan-out width; three things in the design rested on estimates of that cost. `scripts/bench_sandbox_start.py` replaces them with a staged, re-runnable measurement — image composition (base against batteries, on disk against what a pull actually moves, taken from a manifest served by a throwaway local registry rather than from `docker image inspect`), a cold-pull rate measured against a probe image the host has never pulled, cold/warm/hot runs whose per-stage breakdown mirrors `entrypoint.sh` stage for stage, fan-out at N=1/3/5 with a warm cache per sandbox, the thin-base counterfactual, and cost from Cloudflare's published Container rates on the instance type `wrangler.toml` deploys. The 2026-08-21 run is committed beside the summary (`benchmarks/sandbox-start/`, `docs/sandbox-start-benchmark.md`). **Cold 93.2 s, warm 17.8 s, hot 0.18 s**, and 77% of cold is the image pull. The image is **2.90 GB on disk but 1.11 GB on the wire** — the README's "~2 GB" was the wrong number to price a pull with. All three decisions come out *keep*, each with the number behind it: batteries-included wins because a thin base costs **31.9 s per sandbox** and loses from the second one onward (71.9 s once against 25.5 + 31.9N); caches stay out of the image, but the sleep/wake premise underneath them is worth **4.2 s** a run for this repo while the **70.1 s** actually at stake belongs to the image and to platform behaviour no off-platform harness can see; and `[sandbox] setup` earns its place at **0.19 s** when a repository declares nothing, because dependency install is the one stage that degrades under fan-out (13.4 s at N=1, **61.1 s at N=5**) and one legible stop beats five workers discovering the same install concurrently at model prices. What the harness cannot measure it says so about, in its own output. `internal/sandbox/benchmark_test.go` keeps the harness, the raw file and the summary in step, and fails if any of them carries an operator account id.
- **`tk cloud run --max-cost` and `--max-wall-clock` — a budget is now a per-invocation choice** — until now the only budget knob was a deployment-wide var in `wrangler.toml` (`RUN_MAX_COST_USD`, `RUN_MAX_WALL_CLOCK_MS`), so "try this epic cheaply, capped at $2.50 and 45 minutes" meant editing config and redeploying the Worker, then remembering to put it back. Both flags now ride the submit payload (`max_cost_usd`, `max_wall_clock_ms`) into the Run Workflow's config, where the supervision loop already checks them at every observation. **The direction is one-way: a submission may lower a budget, never raise it.** A value above the deployment ceiling is clamped to the ceiling and logged saying so, because the ceiling is the operator's standing decision about how much anything may spend at all, while a submission is something an agent can make — the same asymmetry that keeps sandbox `setup` in PR-reviewed tracked config. Three details that are easy to get wrong and are pinned by tests. An unusable budget is refused at the edge with a 400 rather than dropped and defaulted, because a budget the factory silently ignored is a run the operator believes is bounded and is not. A submitted cost budget counts as *configured*, so it inherits the strict half of the existing behaviour: a run whose AI Gateway cost telemetry cannot be read refuses to boot rather than spending unmeasured, which a deployment relying on the default ceiling does not. And a budget on a `--queue`d submission is stored with the parked entry and travels to ignition, since a budget that survives the submission but not the queue is the same broken promise wearing a delay. Omitting the flags is not the same as passing the deployment's own numbers: an absent budget leaves the deployment's ceiling standing, and nothing about the existing var-only path changes.
- **Pre-flight asserts which pot a run's Workers AI spend comes out of** — an AI Gateway carries a per-gateway `workers_ai_billing_mode`, and it decides where inference bills to. On `postpaid` Workers AI lands on the normal Cloudflare invoice, where an account credit can absorb it; on `unified` the identical traffic drains a **separately purchased prepaid AI Gateway wallet**, bought up front at a 5% premium. Unified Billing is not a discount programme or a payment method for the same invoice — it is a different pot — so one click in the dashboard moves every future run from credit-funded to cash-funded. Nothing would have caught it: the setting is not in `wrangler.toml`, it is not versioned or reviewed, and the gateway logs report the same `cost` in both modes, so a run's telemetry is byte-identical either way. It is now asserted rather than observed. `tk factory setup` reads the gateway object (`GET /accounts/<account>/ai-gateway/gateways/<id>`) with the same Cloudflare API token cost telemetry already needs, refuses to configure a factory whose gateway is not on the mode the operator settled on, and records that mode as `factory_workers_ai_billing_mode` in `~/.ticksrc`; `tk factory status` re-reads it as its own `workers ai billing` rung, which `--check` turns into a nonzero exit. **Postpaid is the default**, so a factory that has never been told otherwise fails on unified rather than quietly spending cash, and an operator who really did buy a prepaid wallet opts in once with `tk factory setup --workers-ai-billing-mode unified`. Three things are deliberate. The assertion **fails closed on a gateway object that names no mode at all** — an absent field is not evidence of postpaid, and a pre-flight that could not read the mode has not passed. Its failures stay in **separate classes** — drifted mode, rejected token, no such gateway, unreadable expectation, no token to read with — because they send an operator to four different places and this repo has already paid for collapsing distinct failures into one message. And a **mis-typed expectation is an error**, not a mode that can never match, so a typo cannot silently turn the assertion into a permanent red nobody can act on. Without a Cloudflare API token there is nothing to read the gateway with: the mode is reported as unchecked, and both setup and status say so rather than passing quietly.
- **Dev builds go to `./bin/tk`, machine-wide installs are asked for** — building `tk` straight over `~/.local/bin/tk` during development replaces the binary every other shell and agent on the machine is using, and silently reverts any hand-applied patch it was carrying; it did exactly that here, reverting a bumped herdr protocol version and obstructing other agents mid-task. The dev path is now a named target — `make build` writes `./bin/tk`, which `.gitignore` already covers — and the machine-wide path is a deliberate one: `make install` delegates to `scripts/install-tk.sh`, which fails closed unless `TK_ALLOW_MACHINE_INSTALL=1` is set and, when it refuses, names `make build` and `./bin/tk` rather than just saying no (`INSTALL_DIR` still overrides the destination). The refusal happens before anything is compiled, so an accidental `make install` cannot half-replace the shared binary. CONTRIBUTING, README and AGENTS.md carry the same note, and `internal/devbuild` pins all three pieces — that no Makefile recipe writes to a machine-wide location, that the guard leaves an existing binary byte-for-byte intact without the opt-in and still installs with it, and that the docs name the dev path.
- **`tk cloud pr-body` — a closeout PR that says what it carries** — a cloud run is submitted from whatever branch the operator was standing on, and its run branch descends from that SHA, so a run submitted off an epic branch that was ahead of the default branch merges that epic to the default branch inside its own PR. That happened: PR 49 (epic `ko8`) was recorded merged at the same second as PR 50 (the run PR for epic `gj9`), by a merge commit nobody made for it, because all of its commits arrived in main inside someone else's PR — approved by a gate that belonged to a different change. The mechanism produced no signal at all. `tk cloud pr-body` writes the closeout PR body and names the cargo: every commit in `<merge target>..<submitted sha>` is listed first, under a heading saying what merging it does to them and how to rebase it away, with the run's own commits below; a PR that carries nothing says *Carried commits: none*, because silence is indistinguishable from not having looked. It reads git and prints markdown — it opens nothing and merges nothing (`tk cloud pr-body | gh pr create --base main --head "$TICKS_RUN_BRANCH" --body-file -`). Inside a run sandbox the defaults come from the container's environment (`TICKS_RUN_BRANCH`, `TICKS_BASE_SHA`, `TICKS_EPIC`), and the closeout prompt now tells the orchestrator to open its PR with it. It fails closed twice over: a merge target this checkout cannot resolve is an error rather than a clean report — a sandbox's shallow clone holds one ref and would otherwise certify every PR as cargo-free — and so is a run branch that does not descend from the submitted SHA, where "what this run created" would be a guess.

- **`[orchestration].max_parallel` is enforced on the dispatch path, not described in a prompt** — the wave width used to be parsed, printed and then ignored: run_62c289d1's boot log announced "wave width 3 from `.tick/runners.toml` [orchestration].max_parallel" and the orchestrator dispatched seven implementers into one 2-vCPU container, more than double the configured concurrent burn on a run that exhausted its budget. Two things were wrong and both are fixed. **The tool was lying about the number:** `tk graph --json` reported the widest wave under the same key name (`stats.max_parallel`) that the config uses for the dispatch width, so an orchestrator told to "launch up to max_parallel" was told 7 by the very tool it asked. The graph now carries a separate `dispatch` block — `max_parallel` (the configured width, 0 when unset), `in_flight`, `in_flight_ids`, `free`, and `now`: the exact ready-wave ids to launch, capped to the free slots — while `stats.max_parallel` keeps its old meaning of graph shape. **And the width is now binding:** the gated act is the CLAIM, `tk update <id> --status in_progress`, which is what every substrate does before it starts a worker (herdr spawn, a harness subagent, a cloud worker container) and the only dispatch signal that is substrate-neutral, durable and visible to `tk`. A claim that would exceed the width is refused with a new exit code 8 (`ExitWaveFull`, its own slot for the reason `ExitTimeout` has one: "wait for a slot" and "that tick does not exist" are different next actions, and an orchestrator must branch on them without parsing stderr), naming the width, its source and the ticks holding the slots. `tk herd spawn` applies the same gate *before* it dials herdr, so a refusal costs zero dials and leaves no half-made workspace. A slot is held by every in_progress non-epic child of the epic and freed by closing or releasing one, so the count is live rather than a budget; re-claiming a tick that already holds its slot is always admitted, so crash-recovery re-dispatch cannot deadlock a full wave. Deliberately not gated: every non-claim edit (a full wave must never make closing or releasing a tick harder — those are what free a slot), ticks with no parent epic (not wave dispatch), and the TUI/board, which are human surfaces. An unset `max_parallel` still means "the adapter decides" and caps nothing.
- **`tk cloud trace <run>` and `tk cloud logs <run>` — reading what a cloud run actually did** — until now nothing could read a cloud run's conversation. `tk factory` had deploy/setup/status and `tk cloud` had run/stop/status, and D1 deliberately holds control-plane state only (runs, signals, dispatch_log, run_gateway_token, run_image, run_progress) — no messages. The record was never missing, though: every model call is proxied through the operator's own AI Gateway, which keeps both bodies and lets them be filtered by the `run_id` the proxy stamps. Two records answer "what happened" and they get two commands rather than one, because a harness that crashed and a model that decided badly are different failures with different evidence. **`tk cloud logs <run>`** serves the harness stream already written to R2 (`GET /api/runs/:id/logs`, `--tail N` for the last lines) — readable mid-run, bounded from the END because the tail is what a run being debugged is read for, and the bound is stated above the output rather than left to be noticed. **`tk cloud trace <run>`** reads the model conversation: message roles, tool calls and their arguments, tokens in/out and cached per call, cost per call, with `--call N` for one exchange in full, `--tools` for just the tool calls, `--cache` for the per-call cache table and `--json` for the raw rows. Two things about it are not obvious and cost real time when guessed at. **Responses are streamed**, so a logged response body comes back with `choices[0].message.content: null` and `tool_calls: null` — reading it and concluding the model emitted nothing is wrong; what the model said is reconstructed from the assistant messages inside each *request* body, deduplicated across calls, because an agentic harness replays the whole conversation every call and so call N's request holds every turn up to N-1 (dedup is by content, not position, so a compacted history keeps its new turns). And **prefix caching is only measurable from `usage_metadata.input_cached_tokens`** on each log row, which makes `--cache` the answer to whether caching is actually hitting — per call, since one changed token near the head of a prompt invalidates the prefix and an average hides exactly that swing (measured by hand on one run: 20 calls, 999,040 input tokens, 446,208 cached, per-call rates swinging between 92% and 0%). The trace reads the operator's own gateway directly with the Cloudflare API token `tk factory setup --cloudflare-api-token` installs, so it still answers when the factory Worker is wedged; a factory without that token has no trace and no cost budget, and the refusal says exactly that rather than reading as "no factory". Paging follows the rule the cost query was fixed to: page until a short page proves exhaustion, and treat the page cap as a failure — a floor presented as a total is what let a truncated query pass a blown budget. **Neither command widens D21's vocabulary.** The operator-to-orchestrator COMMAND surface stays `run`/`stop`/`status`/`answer`: these are read-only observation, they read records a run already wrote, and there is no path from either to the orchestrator — stated in the design doc, in `tk cloud --help` and in a test, so that counting subcommands does not read as a violation.

- **A repo-declared `[sandbox].image` is now booted, not just validated** — the escape hatch existed in config and not in behaviour: a declared image was parsed, validated, reported and warned about, and the Workflow booted the version-pinned base image regardless. The missing half was that the control plane picks an image before it has a checkout to read one from, so it now reads the tracked `.tick/runners.toml` at the **submitted SHA** through GitHub's contents API — before a container exists and before a credential is minted — and boots what the repository declares. Where the value comes from is the same rule `setup` gets and for the same reason: an image *is* arbitrary code, so it comes from the PR-reviewed file at the submitted SHA and never from a submission parameter, which would hand whoever can submit a run the container that holds the run's gateway token and its GitHub credential. Three rules, and the third is the one this tick is about. A repository that declares an image gets it; a repository that declares none leaves the version-pinned base standing; and a declared image this deployment **cannot serve fails the run** with a message naming both references, the file the declaration lives in, the submitted SHA and both remedies — never a silent fall back to the base. "Cannot serve" is the honest phrasing on this substrate: a container's image belongs to the `[[containers]]` application its Durable Object class is bound to, built and digest-pinned by `tk factory deploy`, so honouring a declaration means the operator deployed a factory serving it and named it in `SANDBOX_IMAGE` — which is why that var stopped being descriptive and became load-bearing. Two layers, because the control plane's reader is a **second** reader of a format `tk` owns. Its parse is best effort: a file it cannot fetch or cannot read (GitHub 503, `[[sandbox.setup]]` array-of-tables syntax) leaves the deployment's image standing and says so in the run log, rather than failing a run on a hiccup. What makes that safe is the backstop — the entrypoint compares the declaration, read by `tk` inside the checkout, against the image the control plane says it booted (`TICKS_SANDBOX_IMAGE`) and now **refuses** the boot on a mismatch (exit 6, terminal — a reboot reaches the identical answer) instead of warning and working through it: continuing means provisioning a toolchain, warming caches and spending model budget in an environment the repository explicitly said was the wrong one, and failing later, far from the cause. A boot nothing identified (`TICKS_SANDBOX_IMAGE` unset — the image driven by hand) still warns rather than refusing, because there is nothing to compare against. The two readers are pinned to one another by a shared case file (`cloud/factory/test/fixtures/sandbox-image-cases.json`) that both suites run — a declaration written as a header, a dotted key or an inline table, a commented-out one, and one smuggled inside another table's multi-line notes string, which is exactly what a line-oriented reader would have booted.

- **Per-repo sandbox definition — `[sandbox]` in `.tick/runners.toml`** — a repository now declares what its runs need on top of the batteries-included base image, in tracked config, instead of forcing a factory-wide image rebuild: `image` (optional; absent means the version-pinned base — the 99% path declares nothing), `toolchain` (`tool@version` pins provisioned through the version manager the base image ships, into the project's persistent cache, resolved on first run and warm after), and `setup` (idempotent, cache-populating commands — `pnpm install --frozen-lockfile`, `go mod download` — run once per checkout, in order, after the clone and before the harness). This closes a gap `[environment]` deliberately cannot: an Environment check is verification only ("test, don't ask") and cannot provision anything. One implementation serves both substrates, so a local worker warms identically to a cloud one — the sandbox entrypoint calls `tk sandbox setup` after its clone, `tk herd spawn` calls the same code on a freshly created worktree, and "once" is once per checkout, recorded by a fingerprint of the declared commands in the checkout's *git directory* (never in the worktree, where it would land in a worker's `git add -A`), so a fresh clone warms again and a repeat call is a no-op. `tk sandbox image | toolchain | setup` is the surface, and the entrypoint shells out to it rather than teaching a shell script to parse TOML, so the tracked config has exactly one reader per language. **The security boundary is the reason this lives in tracked config at all:** `setup` runs arbitrary shell inside a sandbox holding the run's gateway token and GitHub credential, so it is read ONLY from the PR-reviewed file at the submitted SHA — never a tick note, a model, a signal payload, an API parameter or an environment variable — and there is deliberately no flag, field or variable anywhere in the path that supplies one. A failing setup command is a stop (exit 6, terminal — a reboot reaches the identical answer), because a wave started on a half-provisioned sandbox fails in every worker at model prices. Booting a *declared* `image` landed separately, below.

- **`tk factory setup` — the factory's credential walkthrough** — a BotFather-style first-run walk that configures a personal factory through prompts alone, shaped exactly like `tk channel setup telegram`: one rung at a time, verified live, then persisted. It checks wrangler auth, offers `tk factory deploy` when nothing is deployed, walks the GitHub credential ladder (a fine-grained repo-scoped PAT is the supported first rung; a personal GitHub App for per-run installation tokens is the documented upgrade path in `docs/factory-credentials.md`), and configures the AI Gateway base URL with the provider behind it — Workers AI needing no key at all, since inference bills to the same Cloudflare account. Each rung is proven against the real service before it is stored: a GitHub API call that also checks the token can *write* to the target repository (a fine-grained PAT that authenticates but was never granted the repo is the classic silent misconfiguration), and a model-list call through the gateway with the provider key. Every credential lands in exactly two places — a write-only Worker secret in the operator's own Cloudflare account and `~/.ticksrc` at 0600 — and never in the repository, which is enforced by a test that runs the whole walk inside a git checkout and fails if any secret appears anywhere under it.

- **AI Gateway routing, per-run attribution, ground-truth cost and the kill switch (D17)** — a cloud run's model traffic no longer carries the operator's vendor key. The sandbox is handed the factory's own `/api/gateway` prefix and a **run gateway token** minted per orchestrator boot; the Worker exchanges that token for the provider key, stamps `cf-aig-metadata` with the run and tick ids the token was issued for (dropping any `cf-aig-*` header the caller sent, so an agent can neither misattribute its spend nor opt out of being attributed), and forwards to the operator's own AI Gateway. Three consequences. A run cannot start without a configured gateway: submission is refused with a 503 whose detail names `tk factory setup`, and a base URL pointed straight at a vendor host is refused as the vendor default it is — the container enforces the same rule at boot. `runs.cost_usd` is read back from the gateway's own per-request logs at every observation, filtered by the run id the Worker stamped, and that number — never an agent self-report — is what the cost budget acts on. And revoking a run's token stops its model traffic mid-run at the credential layer, which works on a wedged or adversarial orchestrator that ignores every message it is sent: every boot rotates (the replaced container's token dies before its replacement's is live), every budget trip and operator stop revokes, and finalize leaves no live credential behind. Closeout gets a fresh token, because a stop must still reach review and closeout. `tk factory setup --cloudflare-api-token` adds the optional half of the gateway rung — a Cloudflare API token with AI Gateway read access, proven with a live log read before it is stored — and a factory without one still routes and attributes model traffic but records each run's cost as unknown rather than as `$0`, which `tk factory status` reports as its own rung.

- **Proof that the cloud harness executes tool calls, and a recording of the shapes it sends** — the first cloud run to complete a real agent turn printed `**Action taken**` above a `tk note …` line whose effect nobody could find, and from outside the container two readings were indistinguishable: the harness ran it against an ephemeral checkout the aborted run never pushed, or the harness narrated a command it never ran. The second would be disqualifying, and a run log cannot settle it — a log is the agent's own account of itself. `scripts/verify-harness-tool-execution.mjs` settles it with side effects that outlive the harness: it substitutes exactly one thing, the model (a local OpenAI-compatible SSE endpoint answering a fixed script, so the tool calls are deterministic instead of whatever a 70B model felt like emitting), keeps everything else real — the real `omp` binary, the `models.yml` wiring `cloud/sandbox/entrypoint.sh` writes, the flags it starts the harness with, a real git repository — scripts a `write` call and then a `bash` call that commits, and then reads the disk and `git log` **after omp has exited**. Both effects are there: the file with exactly its bytes, the commit, a clean tree. The harness executes. Two things it deliberately does not prove, because conflating them sends the next diagnosis to the wrong place: whether a given *model* chooses to emit a `tool_calls` frame rather than prose (a model-quality problem on that rung, identical from outside), and whether a run's tracker writes survive (they do not — nothing pushes the container's checkout, which is the abort path, not the harness). The run also **records** what omp puts on the wire once it has executed a tool, into a scrubbed fixture that `cloud/factory/test/gateway-tool-calls.test.ts` replays through the real `workers-ai` translation: the calling assistant turn carries `content` as an empty **string** (not `null`, not parts) beside a `tool_calls` array whose `function.arguments` is a JSON string, and the result comes back as `role: "tool"` with string content addressed by `tool_call_id`. Content parts were the first place omp was found speaking more OpenAI than Workers AI implements, and tool-call and tool-result messages are where OpenAI-compatible implementations diverge hardest — so this half is a recording rather than a reading of the specification: it says what omp sent, it fails loudly when a new omp sends something else, and it pins that the translation collapses the user turn and leaves every tool field byte-identical.

- **`tk factory status`** — reports each rung (deployment, GitHub, gateway, cost telemetry), what is configured and whether it currently works, following the `tk channel status` pattern: live checks by default, `--offline` to skip them so it is safe with no network, and a rejected credential always reported but only turned into a nonzero exit by `--check`. No credential is ever printed — only the account a token authenticates as, the repository it can reach, and the provider behind the gateway.


### Fixed

- **Budgets and an operator's stop are enforced while a cloud batch is IN FLIGHT, not only between batches (`cloud/factory/src/worker-dispatch.ts`, `run-workflow.ts`)** — the wave loop checked for a hard stop before dispatching each batch and then handed control to `dispatchWave`, whose spawn → confirm → wait → collect → teardown cycle had no way in. An operator pulling the switch, or a budget going over, waited for up to `max_instances` containers to finish — each watched for up to `CLOUD_WAVE_WAIT_TIMEOUT_MS`, thirty minutes — before anything reacted, and the run kept spending the whole time. **This repo has now paid for the same shape three times**: `cts` (a budget whose telemetry could not trip it), `gyl` (a revocation the next boot undid), and this — each time the enforcement existed somewhere that could not act in time. `dispatchWave` now takes a **cancellation seam**: one `Canceller` shared by the whole wave (built by `waveCanceller`), latched so the first worker to see a stop decides it for all of them, deduped so N containers cost one read, and gated to one real read per poll interval. Every polling loop in the cycle sleeps in chunks sized by the canceller's cadence rather than its own, so noticing a stop costs one poll interval and never one batch. A cancelled worker is **torn down before its durable read**, the reverse of the ordinary order: collect's GitHub round trips are seconds a container would keep spending in, and git does not forget while a container dies. A wave cancelled before a container is addressed addresses **none** — `binding.get` provisions, and addressing one is how a stopped run boots the containers it was stopped to prevent. The credential is revoked from the canceller's own hook, ahead of the teardowns (tick `gyl`'s ordering, at wave scale), and again as a checkpointed step so a replayed Workflow does the same thing; the reason a batch was cancelled travels back **inside the step's return value**, because a variable a step's callback closed over is simply not re-assigned on replay and the run would sail into the next batch of a stopped wave. The between-batch check and the mid-batch probe are now the **same function** (`cloudWaveTrip`), which also closes a quieter hole: the wall-clock and cost budgets were enforced by `observe`, and a cloud wave never calls it, so a wave could run every batch it was handed at any cost. **The assertions tick `b6e` declined to write as flaky now exist, on both paths**, through a synchronisation seam the suite did not have: a hook awaited inside the repository-config read (provably before the first credential) and one inside the R2 write that records why a boot died (provably between two boots) order the stop by the code under test rather than by the clock. A hard stop before the first boot credentials nothing; a hard stop between two boots credentials no replacement; a hard stop mid-batch tears the containers down without waiting the batch out — and that last one fails by never finishing if the seam regresses, not by asserting a wrong value.

- **A short run id is resolved, never answered with a confident negative** — `tk cloud trace run_62c289d1` replied *"No AI Gateway calls are stamped with run run_62c289d1"*, which is true of the prefix, false of the run, and read by the operator as "this run produced no telemetry" — the exact opposite of what the command exists to say. The gateway metadata carries the full id (`run_62c289d1e57942cea5fef6c1a508a0fd`), and a truncated id is what an operator actually has to hand after a wrapped terminal line or a copy that stopped at a word boundary. A run id is `run_` plus a UUID with its dashes removed, so anything matching `run_` plus fewer than 32 hex characters cannot be an id and can only be the head of one — that shape is what makes this a recognition rather than a guess, and an argument that was never truncated (a whole id, or anything that is not `run_` plus hex) still passes through untouched and costs no lookup. A prefix is now resolved against the runs the factory knows about — the run index read at its widest window, plus each project's lease holder and queue, since a live run is the most likely thing to have a half-copied id — and the resolution is **reported**, on stderr so that `--json` stays parseable. Ambiguity is refused with every matching id rather than resolved to whichever came back first. And a prefix that matches nothing is refused for being a prefix, in terms that stay honest about what was actually searched: the index is a bounded window, so a miss is a fact about the window and never about the run, and saying "no such run" would only reintroduce the same confident negative one layer down. The same trap was open on the other two run-scoped reads and is closed with them: `tk cloud logs` and `tk cloud status <run>` passed a prefix through to the factory's `no run <prefix>` 404. `tk cloud stop` is deliberately unchanged — it refuses a prefix with an accurate 404 rather than a misleading negative, and resolving a prefix into a kill switch is a decision worth its own tick.
- **The session-affinity key stays per RUN, and the reason is now measured rather than assumed** — under the harness substrate a run is an orchestrator plus N implementer subagents, all spending the same run token, so one `x-session-affinity` value carries N conversations whose contexts share nothing past the harness preamble. The standing suspicion was that they evict each other off the one model instance and that the fix was a key per conversation. Measured, that is not what happens, and the key is unchanged — but the derivation is now a named function (`sessionAffinityKey`) carrying the numbers, so the next agent re-opens it with evidence instead of intuition. In `run_62c289d1` — 230 calls, **65.3% of 10,954,464 input tokens cached, $5.96 against a modelled $15.08 uncached** — the eight conversations separate in the AI Gateway logs by the first two messages of each request body, and the seven-way fan-out phase cached **better** than the serial phase: 67.9% with six or more conversations live against 52.4% while the orchestrator ran alone, and 65.7% for a call whose predecessor belonged to a different conversation against 62.4% for one that followed its own. Interference would have shown the opposite sign. The prompt head was not drifting either: two consecutive requests around a total miss were byte-identical over all 220,891 characters of the earlier one — same tools, same options — and the later call was billed 512 cached tokens of 74,605. Three controlled probes against the same model (four synthetic 15k-token conversations, one shared key against one key each) landed within noise of each other and disagreed on the sign — 24.0/24.3% sequential, 40.2/7.8% concurrent, 12.1/29.8% concurrent with the order reversed — and a fourth showed why: **one** conversation, alone, on its own key still missed completely on two of three follow-up calls. The header buys routing that is real but statistical, so the input a run still pays full price for is instance-side behaviour no key granularity steers, while a body-derived key would hand an agent the choice of its own instance — the property `sanitizedHeaders` exists to deny. Two corrections fall out of the same read: the pre-`l8z` runaway did **not** cache nothing (11,823,872 of 46,098,950 input tokens, 25.6%, with 510 of 892 calls at zero), so the affinity header's real effect is 25.6% → 65.3%; and the log row's `cached` field, which produced the "zero", is the gateway *response* cache and is false on every agentic call by construction — read `usage_metadata.input_cached_tokens` instead.
- **`cmd/tk` command tests inherited the orchestrator's `TK_ACTOR` and blamed the merge** — `TestApproveCommand`, `TestRejectCommand` and `TestUpdateVerdictFlag` went red mid-epic with `expected approve exit 0, got 2`, on a tree that passed on `main`, passed on the same package alone and passed again once the machine was quiet. Load was a coincidence, not a cause, and there was no deadline anywhere near it: the load was *the orchestrated run itself*, and an agent run exports `TK_ACTOR=<runner>:orchestrator` — the form `references/agent-runner.md` mandates and `cloud/sandbox/entrypoint.sh` sets. These tests drive the real CLI, which reads the real process environment, so the verdict guard refused every verdict path for exactly the reason it exists, in three tests that never chose that actor. Three packages' worth of tests were exposed this way (`cmd/tk`, `cmd/tk/cmd`; six tests in total) and `TK_ACTOR=x go test ./...` reproduces it byte for byte. New `internal/tickenv` names the ambient namespace `tk` reads (`TK_`, `TICK_`, `TICKS_` — prefixes keep their underscore so `TICKET_SYSTEM` survives) and both packages scrub it in `TestMain`, so a test sees one of these variables only if it set it itself with `t.Setenv`. A guard test in each package fails with the names of whatever leaked rather than leaving an unrelated verdict test to report a bare exit code, and the guard itself is unchanged: a deliberately runner-shaped actor is still refused, pinned by a test that sets one. **And the message that sent a reader hunting a merge regression is fixed at the source:** `captureStdout` now captures stderr too, and every exit-code assertion in `cmd/tk` reports through `exitInfo`, which renders `got 2 (actor "cloud:orchestrator" is a runner, ...)` instead of a bare `got 2` — an exit code names a category, and several unrelated failures share code 2. The capture helper also drains both pipes concurrently: reading only after the command returned deadlocks the moment a command writes past the 64 KiB pipe buffer, which is the kind of failure a loaded machine really does find first.
- **A budget could overshoot by a full poll interval, because a budget is only as tight as the cadence that samples it** — `detectTrip` runs on an observation and nowhere else, so whatever a run burns between two looks is spent unwatched, and the observation backoff stretches that gap from 15s to a 300s ceiling exactly on the long, expensive runs where it costs the most. Measured on `run_62c289d1`: `RUN_MAX_COST_USD` was 5, `syncRunCost` recorded $5.86 **correctly** — this is not the pagination defect above — and the run was still `running` with no trip. The accounting was right; the cadence was not. The same cadence carries the wall clock, so it overshot the same way: on `run_a1f87597` a 45-minute ceiling was crossed at 11:29:52 and the token was revoked at 11:31:59, about two minutes of unwatched run, because the crossing landed partway through a sleep. Both are now bounded, and deliberately by different means, because the two budgets are known differently. **The wall clock needs no projection** — the deadline is arithmetic on a start time this module measured — so a sleep simply stops at it and the next look is the one that trips: zero overshoot, at no extra observations. **Spend can only ever be projected**, so the sleep before each look is capped at the time the *observed* burn rate says it would take to spend half of what is left (`BUDGET_POLL_HEADROOM`). The remaining headroom halves each look as the ceiling nears, until the cap reaches `MIN_POLL_MS` and the overshoot is bounded by one *fast* poll's worth of burn rather than one backed-off poll's. Against `run_62c289d1`'s shape ($5 ceiling, ~$10.30/hour) that is $0.45 of unwatched spend down to under a cent, for four extra looks out of an allowance of eighty — the tightening is logarithmic, so it cannot exhaust `MAX_OBSERVATIONS` and turn a budget breach into the wrong kind of stop. The rate is measured across the most recent gap rather than averaged over the run, since a run that idles through boot and then burns hard has an average that badly understates the next five minutes; a gap that reads no new spend keeps the last known rate rather than reopening the window, because gateway logs land in batches and a look can legitimately read the same total twice; and a look that read no cost at all (a pass that does not enforce budgets) leaves the previous sample standing, because a missing reading is not a reading of zero. Every input is a checkpointed step result rather than a live `Date.now()`, so a replayed Workflow recomputes the identical cadence. What this does **not** claim to fix: the AI Gateway logs themselves lag, so the floor on any polling scheme is that lag plus one fast poll — bounding the overshoot by a *request* rather than by a timer would need the gateway to refuse once the ceiling is crossed, which is a separate change with its own closeout question (a run whose budget tripped must still be able to spend enough to close out).
- **A run expired its own dispatch lease during boot and hard-stopped itself** — the defect behind the $49.80 runaway, found by the first measured run rather than by any suite. The lease is taken at submit, and until now the next renewal was the *first observation*, which sits behind a whole boot plus a poll delay. A boot that pulls an image, clones at the base sha, installs a toolchain, probes the model and the harness and runs pre-flight takes about a minute — longer than the 60s default the lease was given — so `renewDispatchLease` answered `lease_lost`, `detectTrip` read that as a **hard** trip, and the run revoked its own gateway token roughly a minute in. Measured on `run_d941c5ee`: lease at 08:31:19, token issued 08:31:24, token revoked 08:32:26 `stopped:hard`, and the harness's first real model call answered `403 run_token_revoked` with nobody having requested a stop. This also explains the runaway itself: before the kill-switch fix a lost lease merely ended the pass, so the next attempt booted and minted a fresh credential, forever — a reboot loop that spends and never finishes, which is what 892 calls over 4.4 hours with no completed work actually was. Both halves are needed and neither is sufficient alone: the submission now takes a lease sized to outlive a cold boot (`BOOT_LEASE_TTL_MS`), because a renewal that only happens after the first sleep is always too late; and the Workflow renews the moment the container is up, before that first sleep, because a slow boot outlives any fixed acquire ttl. The regression test inverts the test cadence — a 3s poll against a 1s lease — since the suite's normal 25ms interval cannot express a boot outliving its lease; it asserts the production symptom directly, that nothing revoked the run's credential. Removing either half turns 9 of the file's tests red, which is a fair measure of how load-bearing this lease is.

- **The gateway-token kill switch did not stop a running agent, and a clean stop had no teeth over budget** — found while stopping the $49.80 runaway that `tk cts` explains the start of. D17 says revoking a run's gateway token halts its model traffic even on a wedged or adversarial agent. On the live run it halted nothing: `POST /stop` left the run spending, a hand-written revocation in D1 left it spending for several more minutes, and only `wrangler containers delete` — which removes the application for *every* run and needs a redeploy to restore — actually stopped it. Two independent defects, both fixed. **(1) A revocation was not durable.** The per-request check was correct and stays pinned by a test that revokes mid-run and asserts the very next call through the deployed route is refused with `run_token_revoked` and never reaches the gateway — but the supervisor minted a replacement credential at the next boot, undoing the operator's revocation every time the harness died of it. Worse, the closeout pass enforces no budgets and therefore read no stop record at all, so a run unwinding into closeout re-credentialled itself on every reboot. A hard stop is now a durable refusal to mint: `supervisePass` reads the stop record before it credentials any boot, in every pass, and a hard stop mid-closeout trips the closeout too. **(2) A trip revoked after the grace window.** Finishing in-flight work is right for an ordinary stop and wrong for a run already at twice its budget — the grace window was time the runaway spent. A budget trip, a lost lease and an operator kill now revoke *first* and unwind afterwards, on a container that can no longer spend; a clean stop still revokes at the end of its window so in-flight work can land. **`tk cloud stop <run> --now`** is the operator-facing half (`{"mode":"hard"}` on `POST /api/runs/:id/stop`): it revokes in the request that asks for it, before the state flip and before the Workflow is told anything, and reports how many live credentials it killed. It costs review and closeout — the trade an operator makes knowingly — and both variants now say which stop was performed rather than leaving that to be assumed. Stop mode only escalates: `hard` supersedes a standing `clean` record (an escalation is reported as a new stop, not as one that already stood), `clean` never softens a `hard` one, and an unknown mode is a 400 rather than a quiet downgrade to the stop that does not stop.
- **A cloud run's model calls now carry `x-session-affinity`, so its prompt prefix actually caches** — the largest cost lever found so far. A runaway run spent **$49.80 on 46,098,950 input tokens against 1,019,075 output tokens**: 98% of the spend was re-sending context that never changed, and its input was billed almost entirely uncached — **510 of its 892 calls cached exactly zero tokens, 25.6% cached overall** (re-read row by row under tick fxf; the earlier "not one call hit a cache" reading came from the log row's `cached` boolean, which reports the *response* cache and is false on every agentic call by construction), on a prefix proved byte-identical on two requests hours apart. The prefix was cacheable; nothing was caching it. Workers AI enables **prefix caching** by default on select models, but the cache lives on the model instance, and Cloudflare's own instruction is to "use the `x-session-affinity` header with a unique session identifier to maximize cache hit rates by routing requests to the same model instance". The gateway Worker built the upstream headers (`cf-aig-metadata`, `cf-aig-authorization`) and set no affinity at all, so a run's calls scattered across instances, each meeting a cold prefix. It now sets `x-session-affinity` to the **run id** — the unique session identifier the doc asks for, already on the token row, stable for the life of a run and distinct between runs — and stamps it the same way attribution is stamped: an affinity the caller sent is dropped first, because an agent that could choose its own could park on another run's instance or scatter its own calls, and either costs the operator money. Note the two caches are different things and only one of them matters here: the **gateway response cache** (`cf-aig-cache-ttl`) matches an identical request to a stored response, which an agentic loop never sends twice, and stays deliberately off; **prefix caching** is the one that pays, because the loop's prompt grows by appending while its first tens of thousands of tokens stay fixed. Affinity is only half of it — "a single token difference invalidates the cache from that point onward" — so the other half is now a standing check (`internal/sandbox/prompt_prefix_test.go`) on the one thing the factory itself injects at the head of the message array, the prompt `cloud/sandbox/entrypoint.sh` hands the harness: no date, clock, unix timestamp or uuid in it; two boots of the same run compose it byte for byte identically; and its builders shell out to nothing that varies. The `workers-ai` route, the only body the Worker rebuilds rather than streams, is pinned to rewrite identical requests into identical bytes for the same reason. What this cannot prove from inside is the hit rate itself, which is a measurement rather than a header read: run the same epic twice and compare `cached_tokens` and cost per call — a run whose prefix is 60k of a 70k-token prompt should show most of its input billed at the cached rate from the second call onward.
- **A cloud run pushes its work as it goes, and prints a heartbeat while it thinks** — forensics on a $49.80, 4.4-hour run showed it was never thrashing: it was productively working seven ticks of one epic in parallel worktrees, editing real test files, at roughly $7 of implementation per tick. **None of it survived.** The run pushed nothing, so when the container was destroyed to stop the spend, four hours of work vanished. D4 claims that a run which dies leaves its `.tick/` state "durable, recoverable, and mergeable" on a pushed run branch; that property did not hold, because nothing pushed until closeout and a run that never *reaches* closeout has never pushed at all. The orchestrator container now runs a **run keeper** beside the harness — mechanical, not prompted, for the same reason budgets live in the Workflow (D14): durability that depends on an agent remembering to push is not durability. Every 60 seconds (`TICKS_KEEPER_INTERVAL`) it fast-forward-pushes the run branch `tick-run/<epic>` if it has moved — after each worker branch merges, after each wave integrates — so a killed, evicted or budget-stopped run leaves its completed ticks recoverable on the remote, and the operator stopping a runaway is no longer choosing between an unstoppable run and destroying its work. Merging to the default branch is unchanged: it still waits for closeout and the PR + CI gate, because this is the run's own branch. Four rules keep it safe: pushes are fast-forward only (forcing over a ref this run does not own would lose exactly what the keeper preserves); **nothing is pushed until the run has committed something**, so the ref-comparison that decides whether a run advanced anything (tick ehy) cannot be fooled by a boot staking its branch at the base; a boot that finds the run branch already on origin **continues** it — a rebooted orchestrator, or a new run for an epic whose previous run was killed, checks out what is there and is told in its prompt how many commits it inherited, instead of starting the epic over; and a run branch that does not descend from this boot's base belongs to another run, so it is left untouched and this run pushes to `tick-run/<epic>-<run id>` beside it. The same keeper fixes the other half of that incident: **the output stream froze at offset 3014 for over four hours** while the run was demonstrably working, which is what made killing it look correct — from outside, productive work and a hang were indistinguishable. It now prints one heartbeat per interval carrying elapsed time, HEAD, commits since the base and what the last push did, so liveness reaches the operator on a timer rather than at turn boundaries.

- **A run's cost budget could not trip: gateway spend was read one page deep** — a live run cost **$49.31 against a $25 budget** and kept going for ~4.4 hours, recording $2.98. The recorded number was 6% of the real one, which is exactly 50/845: the pagination in `fetchRunSpend` read `result_info.total_pages`, and the AI Gateway logs API does not send that field. Its `result_info` is `{count, page, per_page, total_count}`, so `total_pages ?? 1` made the loop's `page >= totalPages` true on the first iteration every time and precisely one 50-row page was ever counted. Budget enforcement was therefore disabled for every run past 50 model calls — silently, because the partial sum was returned as a total, and the tests passed against a fixture that had invented the missing field. Paging now ends on the only end-of-log signal the API actually gives, a page shorter than the one asked for, and no code or fixture reads a field the API does not send. **The class is fixed as well as the line:** the page cap (raised from 20 x 50 = 1000 rows to 200 x 50 = 10,000, an order of magnitude past the 887-call runaway) is a runaway guard rather than a truncation policy — a read that reaches it FAILS with a new `truncated` telemetry kind instead of returning what it counted, which a configured cost budget turns into a pre-boot refusal (jk7), and it carries the floor it did count so a mid-run budget still trips on the largest ground truth available (never lowering a larger number already recorded). An under-count that looks like a total is the specific shape of wrongness that cost money, so it can no longer be produced. Consequence worth stating plainly: **every cost figure this factory reported before this fix is low by the same mechanism** for any run that exceeded 50 model calls — `runs.cost_usd`, the run records in R2 and anything derived from them under-report, and the gateway dashboard is the only correct historical record. Regression tests pin the live `result_info` shape verbatim (no `total_pages`), that more than one page is fetched, that a cap-hit is a failure rather than a total, and end-to-end that an 887-call run trips a $25 budget — against the old logic that last test records $2.78 and the run stops only when it runs out of observations.

- **`tk factory deploy` waits for the container rollout instead of returning while the previous image is still serving** — a deploy reported "Factory ready" and exited 0, and a cloud run started immediately afterwards booted the PREVIOUS orchestrator image; waiting and re-running picked up the new one. The tell was exact: two consecutive runs failed with byte-identical harness output, at the same offset, across a deploy that had rebuilt and pushed a new image. The cause is in `wrangler deploy` itself — it builds the image, pushes it, calls `modifyApplication`, POSTs a rollout, and returns as soon as the rollout has been *created*. The Worker and its bindings update promptly; the container application does not, and nothing waited for it. That is the most expensive kind of false signal, because it makes a fix that WAS correct look like it did not work, and the natural response is to go hunting for a second bug that does not exist — which it cost several diagnose-fix-deploy cycles doing. The deploy now reads the digest-pinned image out of the container application block wrangler prints (anchored on the application name, so the hundreds of `sha256:` digests in the Docker build log above it cannot be mistaken for it) and polls `wrangler containers list --json` until that application reports the same digest and is no longer mid-transition. A rollout that does not converge inside the bound, an application the account does not list, or a deploy whose output named no digest all end the command **nonzero with the reason named** — including that the deployment itself landed and nothing needs undoing — rather than as a success nobody can trust; `--skip-rollout-wait` accepts the unconfirmed state deliberately and says so in the output, where "Factory ready" is replaced by "container rollout NOT confirmed". The confirmed digest is printed, recorded server-side (`factory_deployment_image`), and **stamped onto every run at ignition** (`run_image`), so `tk cloud status <run>` names the image that run actually booted — per run rather than per deployment, because what a finished run booted must not move when the next deploy does, and a run with no recorded image says "unrecorded" rather than staying silent about it.
- **A substrate resolution is now always stated, and only a refused assertion is announced — and this repository's own pin becomes `auto`** — two runs end on harness dispatch with no herdr in sight, and they were not distinguishable. `substrate = "auto"` finding no herdr was **silent** by design; `substrate = "herdr"` finding no herdr was a loud explicit degradation. Silence is defensible on a laptop and wrong anywhere the log is the only record — a cloud boot that resolved `harness` gave a reader no way to tell "there was no herdr here" from "nobody looked" — and the same silence covered both the ordinary path and a config that was quietly wrong. Every decision now carries a statement (`Decision.Resolution`, printed by `tk sandbox substrate` on stderr): quiet for `auto` resolving either substrate, for a terminal `harness`, and for a pin that held — naming what was asked for, what the probes found and what is dispatching; loud, unchanged, for a `herdr` pin the environment refused or a `TICKS_SUBSTRATE` the checkout did not ask for. The loud case now also names `substrate = "auto"` as the setting a repository driven both ways should carry, and the durable note tells the two apart: `reason=auto-no-herdr` for the ordinary path, `reason=herdr-unavailable` for the refused assertion. Keeping the registers apart is the point — a repository that announces a degradation on every ordinary run has taught its operator to ignore the announcement that matters. That is exactly what this repository's own `substrate = "herdr"` pin was doing: it is driven three ways (a local harness in herdr panes; a local harness with **no herdr running**, dispatching subagents — the skill's original mode, and the degenerate case the cloud-factory design calls sacred; and a cloud sandbox with no herdr server), so the pin asserted something untrue of two of them, announced a broken assertion on every local run without herdr, and stopped the first cloud run outright. It is now `auto`, which probes and resolves all three correctly. `runners-config.md` gains the two-register table, the *Pin, or `auto`?* authoring rule, and — because it was proposed and rejected on enumeration after that cloud run — the reasoning for why there is deliberately **no** "where am I running" signal: `auto` already answers correctly inside a herdr pane, outside one with herdr running, outside one without it, and in a container, so a location variable would duplicate a probe, and it would answer wrongly for a local orchestrator driving cloud workers (D19), which is a supported configuration rather than a hypothetical. What a probe genuinely cannot settle — "herdr is reachable but should not be used here" — is what `TICKS_SUBSTRATE` is for.

- **A cloud run resolves the harness substrate instead of aborting on a repo's local herdr pin** — the first cloud run that completed a real agent turn booted, cloned, resolved its model, made a successful model call, read `.tick/runners.toml`, found `substrate = "herdr"`, correctly discovered there is no herdr socket in a container, and stopped — citing the orchestration protocol and recording the runner-state note in the documented format. The agent behaved exactly right; the configuration was what was wrong. Phase 1 of the cloud factory runs "the existing harness substrate (subagents) inside one container", and herdr-in-the-cloud is a door deliberately left open rather than a deliverable, but nothing told the container that: it read a pin written for the repository's LOCAL runs and stopped. The fix is an explicit override, not a rewritten checkout — editing the tracked file inside the container would change the base every worker commits against and put a config change nobody submitted into the run's diff. `TICKS_SUBSTRATE` (`herdr | harness | auto`) now replaces `[orchestration].substrate` for one run, honoured by the Go decision procedure (`DecideOverride`), by the new `tk sandbox substrate` — two lines on stdout, the resolved substrate then the `runner-state:` note line, with the reasoning on stderr — and by the ticks skill, whose substrate decision now starts with the override. The sandbox entrypoint defaults it to `harness`, exports it so everything the harness spawns resolves the same substrate, prints the resolution and the note line in the boot log, and carries both into the orchestrator's prompt with the instruction to record the note on the epic: the protocol requires explicit degradation to be announced and noted, and an override — a deliberate choice rather than a degradation — is held to the same rule, because a substrate nobody announced is one nobody can audit once the sandbox is gone. Fail-closed either way: a value that is not a substrate stops the boot naming the variable (exit 2) rather than falling back to the file, and `TICKS_SUBSTRATE=herdr` in a container still gets the documented explicit degradation instead of a stop. The other `[orchestration]` key a cloud boot inherits, `max_parallel`, is honoured as-is and printed with the resolution — under the harness substrate it is concurrent subagents inside one sandbox rather than independent panes.

- **A cloud run on the Workers AI rung can now make its first model call** — the furthest a live run had reached: container boot, clone, 3/3 pre-flight, model resolution, omp's own provider wiring and a GREEN gateway probe all passed, and then the first real completion came back `400 AiError: Bad input: oneOf at / not met … Type mismatch of /messages/0/content, array not in string`. The design doc's claim that Workers AI models "speak the OpenAI-compatible shape" was doing more work than the endpoint supports: Workers AI's `/v1/chat/completions` takes `messages[].content` as a **string**, while omp sends OpenAI content parts (`[{"type":"text","text":"…"}]`) for user messages and a plain string for the system message. omp has no setting for the wire shape of message content — its provider config takes `baseUrl`, `api`, `apiKey`, `models` and a `compat` block, and that block has no such key — and swapping harnesses for this one rung would make the no-key rung the only one that cannot run the default kind. So the dialect is normalised at the hop that already reads every model request: the factory's gateway Worker collapses content parts into a string on the `workers-ai` route and nowhere else, leaving a conforming body byte-identical and every other provider's body streamed through untouched. A part with no string form — an image, audio, a file — is **refused** with a 400 naming the message index and the part type, because the standing risk of a translation layer is that it silently drops what it cannot express and reaches the model as a prompt with a hole in it. `docs/design/cloud-factory.md`, `cloud/factory/README.md` and `cloud/sandbox/README.md` now read "OpenAI-shaped, with one documented difference handled at the proxy".

- **A repo routed at Workers AI can name its model** — every Workers AI model id begins with `@` (`@cf/openai/gpt-oss-120b`), so the provider-qualified form `.tick/runners.toml` carries is `workers-ai/@cf/openai/gpt-oss-120b` — and the `Model` pattern, written for `vendor/model` shapes, had never met a namespace sigil and rejected it: a factory configured for the design's no-key provider rung could not put that provider's model in `[orchestrator].model`. A segment may now lead with `@`, in that position and nowhere else — `workers-ai/cf@openai/…` and `workers-ai/@/…` are still stops, so the id stays a real constraint rather than a string with a hole in it. Fixed in all four readers that must agree or one file becomes valid for one and invalid for another: `runners-config.schema.json`, the Go loader, the Python reference validator and the pi extension, each with the real id as a test case and the malformed ones held negative. The sandbox entrypoint already declined to prefix a namespace an id carried, so the explicit form flows through untouched; an id that omits the constant `@cf/` still resolves, and `runners-config.md` now states the grammar.
- **A cloud orchestrator no longer boots with a gateway and no model to call** — the first live run to reach the skill loop cloned at the submitted SHA, passed all three environment checks, started the harness, and then sat at "Working..." producing nothing: the container exported gateway base URLs and the run token but `TICKS_MODEL` was empty, there was no `workers-ai` route at all (the documented no-key rung), and a harness with no model does not fail — it hangs, which is worse than an error and exactly the silence the green-start trap exists to catch. Three changes close it. **The model comes from routing:** when the control plane sets none, the entrypoint asks the checkout through the new `tk sandbox model`, which reads `[orchestrator].model` from `.tick/runners.toml` and otherwise resolves role `orchestrator` at the `frontier` tier, falling back to `[roles.implement]` like any unnamed role — so the orchestrator is routed by the same table as every other role. **The provider is part of the model id:** a qualified id (`workers-ai/…`, `anthropic/…`, `openai/…`, `openrouter/…`) selects the gateway route, a bare `claude-…`/alias or `gpt-…` id is recognised as its vendor's, and anything else stops the boot rather than guessing a route; `WORKERS_AI_BASE_URL` is now exported alongside the other three, a Workers AI model repoints `OPENAI_BASE_URL` at its OpenAI-compatible `/v1` route (Workers AI has no vendor variable a harness reads), and the `@cf/` namespace the routing schema cannot spell is restored from `workers-ai/meta/llama-…`. **The route is proved, not assumed:** one bounded, one-token completion goes through the gateway with the run's own credential before the harness starts — the same content gate `tk herd spawn` applies to workers — and a refusal is quoted verbatim with its status, because the factory's gateway errors name `tk factory setup` themselves. Every unusable configuration is now exit 7 with a message naming the file to edit: nothing routed, an unreadable config (told apart from a missing model), a provider that cannot be derived, a `claude` harness paired with a non-Anthropic model, a refused probe, and a gateway that never answers. It runs before toolchain provisioning, setup and the pre-flight, because a run that cannot make a model call is over whether or not its toolchain installed.

- **The pi runner refuses a role written for another kind, instead of handing its model id to `pi`** — `.tick/runners.toml` has one `[roles]` table and more than one reader: `tk herd spawn` compiles a cell into a herdr spawn of that `kind`, while the pi extension behind `/ticks-plan` and `/ticks-run` compiles the same cell into `pi --provider/--model/--thinking` in its own process. Because `model` lives in the kind's own namespace, one table cannot carry a herdr routing and a pi routing at the same time — and the migration off `## Pi Orchestrator` made that concrete: a repo whose roles are `claude`/`codex` had `sonnet:high` and `gpt-5.6-luna:max` resolving straight into `pi --model`, with no provider at all, on every role the deprecated block used to own. The pi reader now takes only `kind = "pi"` cells. Any other kind is **refused, not dropped**: no model is derived from it, the refusal names the cell, the kind and the model it would have passed (`roles.implement.tiers.balanced: kind = "codex" … refusing to derive implement_balanced_model = "gpt-5.6-luna:max"`), and the run blocks with nothing authorized — quietly leaving the model unset would just run the tick on pi's own default, the same silent substitution the spawner refuses for an impossible cell. A tier that crosses kinds is refused at the tier, leaving its sibling tiers intact; `harness = "pi"` does not license another kind; the deprecated markdown block, which was pi-only by its heading, is unaffected. `runners-config.md` → *One table, one kind per reader* documents the rule and the reader/spawner split it belongs to.

- **`.tick/runners.toml` version gate — an older `tk` now says "upgrade", not "57 unknown keys"** — the command surface (`[testing]`, `[evidence]`, `[environment]`) makes a config file that a previous release cannot read, and until now it did not degrade: every `tk herd` command on an older binary died with *"57 validation errors: environment.commands: unknown key; …"*, naming no cause and no fix, the moment somebody ran `tk config migrate`. The compatibility direction that was designed (a new `tk` reading a legacy `config.md`) was fine; its mirror image was never tested. A file carrying the command surface is now **version 2**, every reader — the Go loader and the pi runner's TypeScript one — checks `version` **before** shape, and a file newer than the binary is refused with exactly one line: `.tick/runners.toml is version 2 and this tk understands version 1; upgrade tk (tk upgrade)`. Within a version the reader understands nothing is relaxed: a typo'd key is still a stop that names the key. `tk config migrate` writes the new version — including for a repo an earlier migration already moved, which is otherwise stranded at `version = 1` with version 2 content — and warns that every other checkout needs tk 0.32.0 or newer before the file lands there.

### Added

- **The operator channel: autonomous runs can reach the human who launched them** — `tk channel setup telegram` pairs a personal bot (token → `getMe` → one-time `/start` code; secrets land in `~/.tick/operator.json` at 0600 with a `TK_HOME` override, never in the repo — a token-shaped string in the tracked mapping is rejected on load *and* save), and three commands use the pairing: `tk tell` for one-way announcements, `tk ask` for questions that park a tick awaiting and block until answered, and `tk answer` as the terminal twin. The epic close-out gate audit accepts a channel press for the same reason it accepts nothing else: the CLI will not let a runner manufacture the claim. (The final review of this epic caught precisely that forgery path in an earlier draft — `tk answer` clearing a gate without the guard — and it was closed before merge.)

Adds a three-way triage of every anticipated human touchpoint (resolve questions now, do human setup tasks now, reduce approvals by converting to a test / pre-authorizing / agreeing the bar / batching), a frontier-based question algorithm (compute the frontier of decisions whose prerequisites are settled, prune branches the work itself will answer, look facts up rather than asking, ask the whole frontier in one numbered message with a recommendation each, repeat until empty), graph-shaping rules for the survivors (ask early / block late, split around the decision, target the interface, scrutinize gate edges), a Step 6 in the foundation-first procedure, a *no unresolved decisions* line in the Definition of Ready, and two anti-patterns. The epic retro now treats a mid-run `--awaiting input`/`escalation` as a planning-quality signal into `.tick/learnings.md`.

### Fixed

- **Only a human can clear a human gate** — `ProcessVerdict` closed an `awaiting work` tick on any `approved` verdict without checking the actor, so an orchestrator running as `TK_ACTOR=<runner>:orchestrator` could `tk approve` its own human tick; the tick graph's "a human must do this" edge had no teeth at the state-machine layer, and the routing error even advertised `tk close --force` as a bypass. A verdict from a runner-shaped actor (colon-scoped, or ending in `orchestrator`) is now refused on `tk approve`, `tk reject`, `tk update --verdict`, `tk close --force` over a `--requires` gate, plain `tk close` on an already-`--awaiting` tick, and an epic `--force` cascade over any gated child. `--actor` is provenance rather than authorization, so a runner-shaped `--actor` is refused too. Unchanged: `tk close` on a `--requires` tick that has not been routed yet still routes it to a human — the agent's normal path. `--from human` is the only attestation and stamps the activity actor `human` rather than the runner name, the same durable provenance boundary `tk note --from human` already established. The state machine stays pure: it is shared by the CLI, TUI, tickboard server and cloud client, which have different provenance stories, so the check lives at the write path. This is deliberately not tamper-proof — a local CLI cannot stop an agent from typing the flag — so epic close-out gains a **gate audit** asserting every gated tick was cleared by a human actor, fail-closed like Acceptance Evidence.

## [0.22.0] - 2026-08-12

### Added

- **Dashboard worker timers** — each worker row in `tk herd dashboard` now carries an elapsed-time summary (`working 4m12s · age 9m01s`): time in the current status, and total age since the manifest was written. A worker stuck in one status is the thing an operator is watching for, and a static status column never showed it.

### Changed

- **Normalized `ExitNoRepo` / `ExitNotFound` across every command** — `approve`, `reject`, `merge` and the `tk herd` family already returned typed exit codes for "not in a git repository" (3) and "no such tick" (4); the ~25 other commands wrapped the identical failures with a bare `fmt.Errorf` and exited 1, so an orchestrator could not branch on either condition without parsing message text. Classification is now central: `repoRoot()` itself returns `ExitError{ExitNoRepo}`, and every tick lookup goes through `notFoundIfMissing`, so a command added later inherits the codes instead of opting in. No condition changed from success to failure or vice versa — only the code each failure reports. Observable changes:
  - `tk init`, `create`, `show`, `update`, `close`, `reopen`, `delete`, `block`, `unblock`, `note`, `notes`, `list`, `ready`, `next`, `blocked`, `label add|rm|list`, `labels`, `deps`, `graph`, `roadmap`, `status`, `stats`, `rebuild`, `migrate`, `gc`, `import` and `tui` run outside a git repository now exit **3 (no repo) instead of 1**. Rationale: exit 1 is "the command ran and failed"; an orchestrator that sees 3 knows to fix the working directory rather than retry or escalate.
  - `tk skills install` / `tk skills diff` with no `--dir` and no enclosing git repository now exit **3 instead of 1**, matching every other command's no-repo failure. Rationale: the two commands' own `--help` used to fold "not inside a repo" together with "neither convention directory exists", which are different faults with different fixes (chdir/`--dir` vs. create a skills directory); the latter still exits 1.
  - `tk show`, `update`, `close`, `reopen`, `delete`, `note`, `notes`, `deps`, `graph`, `label add|rm|list`, `block` (target or any blocker) and `unblock` given an id that names no tick now exit **4 (not found) instead of 1**. Rationale: "this id does not exist" is a recoverable, distinguishable outcome — an orchestrator can create the tick or correct the id — and reporting it as a generic failure sent every such caller down the retry path.
  - `tk roadmap <epic>` for an epic absent from the roadmap now exits **4 instead of 1**, for the same reason.
  - Unchanged on purpose: a tick file that exists but cannot be read or parsed still exits 1, never 4 — this is the boundary `tk herd collect` already draws for run manifests, because a caller reading 4 as "never created" would act on damaged state instead of stopping.

### Fixed

- **Codex workers can commit from a linked worktree** — a codex worker started with the verified full-auto pair (`-a never -s workspace-write`) did its work and then could not commit it: a linked worktree's `.git` is a file pointing at `<git-common-dir>/worktrees/<name>/`, so the index, refs and objects a commit writes all land outside the sandbox. `tk herd spawn` now grants that one directory with `--add-dir <git-common-dir>` (resolved with `git rev-parse --git-common-dir`, never assumed to be `<root>/.git`), keeping the sandbox rather than dropping it. Kinds that need it fail closed: an unresolvable path refuses the spawn instead of starting a worker that cannot commit.
- **`tk herd cleanup` no longer stalls on the worker's own RESULT file** — the worker template deliberately leaves `RESULT-<tick-id>.md` uncommitted, and worktree removal (never forced) refuses any dirty worktree, so every cleanup after a successful run failed at remove-workspace. Cleanup now archives that file beside the run manifest as `<tick>.RESULT.md`, removes it and proceeds — only when it is the sole change in the worktree. Any other modification or untracked file still refuses exactly as before; the no-force guard is unchanged.

- **Deterministic implementation capability routing** — public graph tasks now include description, acceptance criteria, type, and labels. - **Typed exit-code classification** — `tk`'s exit code now comes only from an `ExitError` found in the error's unwrap chain (`errors.As`); the message-substring heuristics that used to infer exit 2 from text like `accepts N arg(s)`, `unknown flag`, or `invalid argument` are gone. Cobra's flag-parse failures and positional-argument validators are converted to `ExitError{Usage}` where they occur, so genuine command-line mistakes still exit 2. Two observable changes follow:

Rationale: exit 2 tells an orchestrator to fix its command line; the command line was correct and the fault was environmental, so the old code sent every such caller down the wrong recovery path.
  - A command that takes no positional arguments (`tk list stray`, `tk status extra`, …) now exits **2 instead of 1**. Rationale: `cobra.NoArgs` phrases its rejection as `unknown command …`, which matched none of the old substrings, so an arity mistake that every sibling validator reported as usage was reported as a run failure.
